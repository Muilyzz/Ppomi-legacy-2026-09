# Ppomi 0.1.0 출시 점검

2026-09-06 로컬 저장소와 GitHub 릴리스 확인 기준. `backlog.md`는 9월 3일 자산관리 중심의 이전 계획이며, 현재 출시 상태는 이 문서를 먼저 참고한다.

## 화면을 덮는 전체화면 키오스크 복원

일반 모드는 미러링 바로 뒤의 단일 창을 유지한다. 초록 버튼이나 `⌃⌘F`로 들어가는 전체화면은 현재 디스플레이 전체(`NSScreen.frame`)를 네 개의 높은 레벨 패널로 덮고, 실제 미러링 창 영역만 비워 둔다. 메뉴 막대와 Dock도 덮는다. 미러링을 반복 활성화하거나 위치를 고정하지 않으며, macOS의 Space·앱 전환 제스처는 차단하지 않는다.

아무 키나 누르거나 빈 배경을 클릭하면 우측 상단에 **X**가 나타난다. X를 누르거나, X가 보이는 상태에서 Esc를 누르거나, `⌃⌘F`를 누르면 일반 창으로 돌아간다. 키를 길게 누른 자동 반복만으로 모드를 반복 전환하지 않는다. X는 48pt의 독립 창이어서 폰이 화면 높이를 거의 채워도 잘리지 않는다. 폰이 사라지거나 다른 앱에 가려지면 해당 영역도 덮고 X를 표시한다.

기존 작업대와 사람 승인 뷰를 그대로 옮겨 타임라인 문서와 대기 중인 승인을 유지한다. 일반 창의 숨겨진 레이아웃은 이때 멈춘다. 앱 숨기기를 주기 검사로 되돌리지 않으며, Space·디스플레이 구성이 바뀌거나 파일 선택·설정 창이 키 윈도우가 되면 전체화면에서 나온다. 이 경우 미러링을 다시 활성화하지 않는다.

전체 Swift 테스트 109개가 통과했다. 덮개 면적·음수 원점 디스플레이·화면 밖 폰·48pt 종료 버튼·Esc 자동 반복·동일 뷰 재사용·숨겨진 호스트의 레이아웃 중단과 복원을 합성 데이터로 검증했다.

같은 서명을 유지한 설치본에서 초록 버튼으로 진입한 뒤 WindowServer가 네 덮개를 레벨 1000, X를 레벨 1001로 표시함을 확인했다. 1728×1117 디스플레이에서 미러링 446×978 영역을 제외한 면적을 정확히 덮었다. 빈 배경 클릭으로 X가 나타났고, 우측 상단 X를 좌표로 눌러 일반 창으로 복귀했다. 타임라인 스크롤 막대 값 0.5984252가 진입 전과 복귀 후에 같았으며, 이 과정에서 추가 페이지 로드는 없었다. 화면 제어 도구의 대상 지정 키 입력으로는 전역 키 감지 경로를 확인하지 못했으므로, 실제 키보드로 X 표시와 Esc 종료는 사용자 확인이 남아 있다. Space·디스플레이 변경 및 파일 선택 창의 자동 복귀도 실행 검증하지 않았다.

아래의 “단일 배경 창으로 변경” 절은 이번 복원 전 단계의 기록이다.

## Dock에서 작업대 다시 열기

Dock 아이콘을 눌러도 작업대가 보이지 않는 원인은 `showMain()`이 미러링 창의 존재만 확인하고 다른 앱에 가려졌는지는 확인하지 않은 데 있었다. Dock으로 활성화된 뽀미를 이미 가려진 미러링 아래로 다시 내려보냈다.

명시적인 다시 열기에서는 미러링의 숨김·최소화를 복원하고 기존 창에 `AXRaise`를 한 번 보낸다. 다른 앱의 일반 창보다 앞으로 왔는지 확인하며, 필요할 때만 기존 활성화 경로를 한 번 사용한다. 그 뒤 같은 뽀미 창을 미러링 바로 아래에 놓는다. 실패하거나 전환 중이면 뽀미는 독립적으로 표시하고, 주기 검사에서는 미러링이 실제로 앞에 왔을 때만 다시 연결한다. 다시 열기 직후 2초 동안 일시적인 미러링 누락 때문에 작업대를 숨기지 않으며, 사용자가 앱을 숨긴 동안에는 주기 검사로 다시 올리지 않는다. 탭·키오스크 모드·기존 창은 유지한다. 일반 탐색 클릭과 주기 검사에서는 이 앞으로 가져오기 경로를 실행하지 않는다.

`applicationShouldHandleReopen`은 Dock 및 Finder에서 실행 중인 앱을 다시 여는 요청을 처리한다. [Apple 문서](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationshouldhandlereopen(_:hasvisiblewindows:)). `AXRaise` 성공 자체를 창이 보인다는 증거로 삼지 않고 WindowServer 순서를 확인한다. 활성화 fallback에는 기존 최대 약 4초 대기가 남아 있다.

Dock 재열기 수정본 설치 후 사용자가 다른 앱을 보고 있는 상태에서 Dock 아이콘을 눌러 **뽀미와 미러링이 둘 다 나타난다**고 확인했다. Finder에서 설치 앱을 선택해 다시 연 실행 검사에서도 `app.reopen` → `reveal.presented(phonePresented: true)`와 같은 창 번호 유지가 기록됐다. 이때 활성화 fallback 없이 약 4ms 내에 앞으로 가져온 것으로 확인됐다. 최소화와 별도 Space에서의 복원은 실행 검증하지 않았다.

## 타임라인 스크롤 중 반복 새로고침 수정

Dock 재열기 확인 후 사용자가 타임라인 스크롤만 덜덜거린다고 보고했다. 실제 설치본의 선택적 `web.load`·`web.ready` 기록에서 조작 없이 82.46초 동안 3,512회 페이지 로드가 관측됐다. `TimelineView`가 상태 변경마다 HTML을 만들 때 JSON 딕셔너리 순서가 달라져 WebPage가 이를 새 문서로 판단했다. 새 문서의 `showDay(today)` 메시지는 같은 날짜도 다시 상태에 발행했고, 이 과정이 반복됐다. 스크롤 도중 문서 자체가 계속 바뀌는 원인이었다.

타임라인 JSON 키 순서를 고정하고 HTML은 최초 표시 또는 장부 버전 변경 때만 만든다. 같은 날짜 메시지는 상태를 다시 발행하지 않는다. 날짜 선택·증빙 이동 경로는 유지하며 AppKit 내부 스크롤 뷰나 DOM 구조는 바꾸지 않았다. 전체 Swift 테스트 101개가 통과했다. 동일 장부 100회 렌더링의 바이트 안정성, 동일 날짜 100회 수신 시 재발행 없음, 실제 날짜 변경과 증빙 이동을 합성 데이터로 검증했다.

설치한 수정본에서 타임라인 표시 후 76초 이상 추가 페이지 로드가 없었고, 스크롤 막대를 0.7519685 위치로 옮긴 뒤 대기해도 같은 값이 유지됐다. 검사 중 사용자가 탭을 바꿨을 때의 최초 페이지 로드는 정상 동작으로 구분했다. 이는 반복 새로고침과 스크롤 위치 유지 검증이며, 모든 트랙패드·마우스 제스처에서의 창 순서까지 무조건 보장하는 결과로 해석하지 않는다.

## 클릭 중 포커스·창 순서 보완

단일 창 전환 후에도 사용자가 클릭할 때 미러링이 움찔한다고 보고했다. 이전 실행 확인은 클릭이 끝난 뒤의 좌표를 비교한 것이므로, 클릭 순간의 포커스나 창 순서 변화가 없었다는 증거로 간주하지 않는다.

작업대의 SwiftUI·보고서 웹 뷰·배경·승인 버튼은 클릭의 자동 창 올리기를 미루고 해당 마우스 동작에서 취소하도록 수정했다. 다른 앱을 사용 중일 때 일반 탐색이 뽀미의 키보드 포커스를 자동으로 요구하지 않도록 했으며, 뽀미를 직접 활성화하거나 입력 필드를 사용하는 경로는 유지한다. Stage Manager가 미러링의 실제 창을 잠시 보고하지 못할 때는 기존 연결을 0.5초간 유지해 즉시 숨김·재표시하는 것을 피한다.

전체 Swift 테스트 94개가 통과했고 같은 개발 서명 요구사항을 유지한 수정본을 설치했다. 잠금 해제 후 화면 제어 도구의 좌표 클릭으로 보고서 본문·절차·타임라인을 비교했다. 수정 전에는 뽀미가 미러링 위로 올라가는 상태가 두 차례(표본 간 약 9ms·66ms) 관측됐으며, 수정 후 같은 클릭 순서에서는 관측되지 않았다. 두 빌드 모두 클릭 구간의 폰 좌표는 일정했고, 수정 후 탭 전환 및 창 올리기 지연 콜백 적용을 확인했다.

이 비교에는 화면 제어 도구의 앱 활성화·준비 클릭이 섞여 있다. 수정 후에도 도구가 이미 뽀미를 활성화한 상태에서 웹 뷰가 키 포커스를 얻었고, 다른 창이 두 앱 사이로 들어올 때 순서를 보정하는 동작은 남아 있다. 따라서 일반 사용자 클릭에서 움찔 현상이 완전히 사라졌다고 판정하지 않는다. 창 순서는 약 120Hz로 샘플링했으므로 더 짧은 변화는 놓칠 수 있다. 플레이북 카드 상세 확인은 화면 제어 연결 오류로 완료하지 못했다.

`PPOMI_WINDOW_TRACE=1`로 실행하면 로컬 표준 오류에 클릭·키 포커스·창 순서·좌표 변화를 기록할 수 있다. 기록은 기본적으로 꺼져 있으며, 창 제목·화면 내용·입력 문자열은 포함하지 않는다. 로컬 측정 로그는 공개 저장소에 넣지 않는다.

## 단일 배경 창으로 변경

2026-09-06 키오스크와 일반 창을 미러링 바로 뒤에 놓이는 하나의 `MainPanel`로 통합했다. 같은 일반 창 레벨 안에서 앞뒤 순서를 유지하며, 키오스크 전환은 현재 화면의 사용 가능한 영역(`visibleFrame`)으로 같은 창을 확대한다. 별도 Space나 네 개의 `.screenSaver` 패널을 만들지 않고, 전역 제스처 차단과 반복적인 포커스 고정을 제거했다.

초록 버튼·`⌃⌘F`로 전환하고, 확대 중에는 **창으로 돌아가기**도 사용할 수 있다. Dock 아이콘으로 다시 열면 같은 창과 현재 모드를 유지한다. 사람이 미러링 창을 직접 옮겼을 때는 폰을 원래 위치로 되돌리지 않고 뽀미 배경 또는 옆 열 배치가 따라간다. 상태 안내와 사람 승인 버튼은 폰 옆 열 하단에 두어 키가 큰 폰 아래로 숨지 않게 했다.

변경 후 확인한 결과:

- `swift test --package-path Ppomi`: 전체 87개 통과, 실패 0.
- 이전과 같은 Apple Development 서명 요구사항을 유지한 빌드로 설치·재시작했고, 손쉬운 사용·화면 기록 권한이 유지됐다.
- 실제 설치 앱에서 초록 버튼으로 같은 “뽀미” 작업대 창이 확대되고 **창으로 돌아가기**가 표시되는 것을 확인했다. 확대 상태에서 타임라인·절차 탭을 전환해도 미러링 위치가 유지됐으며, 복귀 버튼으로 일반 창의 원래 도킹 위치로 돌아왔다.
- 폰은 `IN_USE` 상태였으므로 폰 앱 안의 작업이나 결제는 실행하지 않았다. 수동 폰 이동을 따라가는 배치 계산은 회귀 테스트로 확인했다. 화면 제어 도구의 드래그로 실제 창이 이동하지 않아 직접 드래그 추종은 실행 검증하지 못했고, Space 전환도 실행 검증하지 않았다.

- 최초 배포는 `Not authorized`로 실패했으나, `hub/`에서 `vercel deploy --prod --yes --scope muilyzz`로 팀을 명시해 배포 성공. `https://ppomi.muilyzz.com` 응답에서 수정된 안내 확인.

- 실폰 MCP 검증 완료: `phone_open`으로 여기어때 열기, 홈의 검색 탭 누르기로 발자국을 자동 기록했다. 홈으로 돌아와 `run_combo(app: 여기어때, max_steps: 1)` 호출 결과 `⊙ ^검색$ ✓`, 검색 화면 도착 및 걸음 수 제한 정지를 확인했다. 같은 검색 화면에서 다시 호출하자 `아는 화면이 아님`으로 추가 조작 없이 정지했다.
- 검증 범위는 비결제 탐색 한 걸음 재생과 미등록 화면 정지다. 결제·사용자 차례 정지는 단위 테스트만 통과했으며 실폰 검증 및 데모 영상은 아직 완료하지 않았다.
- 자동 기록된 JSONL 발자국은 로컬 보관하도록 Git 제외. 화면 증거도 기존 `data/shots/`에 로컬 보관한다.
- 플레이북 공통 카탈로그: `Ppomi/Sources/Ppomi/Catalog/<id>/`의 명세·아이콘·사용법을 키오스크, MCP, 앱 열기 및 수집 설정이 함께 읽는다. 새 앱 폴더는 키오스크에서 가져오며 코드 수정·재빌드 없이 등록된다. 허브 배포는 같은 원본에서 검증된 파일만 복사한다. 형식과 범위는 [플레이북 패키지 v1](playbook-format.md)을 참고한다.
- 기존 이름 기반 `.md`·`.jsonl` 기록을 보존하고 고정 앱 ID로 연결한다. 재생 배지는 현재 패키지 버전에서 실제 재생된 동작만 센다. 이전 누적 성공 횟수는 전체 절차 완료나 현재 버전의 재생 성공을 증명하지 않는다.
- 도킹 초기화 수정: 메인 패널 할당 이후 최소 크기와 폰 영역을 배치하며, 손쉬운 사용 권한이 없으면 반복적인 창 전환·숨김 시도를 멈추고 원인을 안내한다. 초록 버튼의 클릭·접근성 누르기 동작을 포함한 `KioskGeometryTests` 2개와 `AppDelegateTests` 3개 통과(위 전체 테스트 80개 이후 별도 실행).
- Swift 빌드에 plist·entitlements·로컬 JSON 파일의 미처리 파일 경고가 남아 있음. 빌드와 테스트 실패는 없음.

## 개발 서명 전환 후 권한 복구

2026-09-06 애드혹 빌드를 Apple Development 서명으로 교체한 뒤, 시스템 설정에서 허용 표시가 있어도 앱의 손쉬운 사용·화면 기록 검사가 실패했다. `tccd` 로그는 현재 앱을 `com.muilyzz.ppomi`로 정확히 식별하면서, 저장된 애드혹 `cdhash` 조건과 새 개발 서명 요구사항이 일치하지 않아 거부한다고 명시했다. 같은 표시 이름의 옛 앱도 설치돼 있었지만 이번 거부의 확인된 원인은 남아 있던 서명 조건이다.

현재 앱의 `Accessibility`와 `ScreenCapture` 권한만 `tccutil`로 초기화하고 `/Applications/뽀미.app`을 정확히 재등록했다. 이 `tccutil`은 애드혹→개발 서명 전환 사고의 **일회 복구**였고, 셸/`scripts/install-shell.sh`의 일상 절차가 아니다. 사용자 인증·허용 후 앱을 재실행하자 권한 없음 안내가 사라지고 실제 폰 상태인 “손에 든 iPhone · 잠그면 돌아옴”이 표시됐다. 기존 앱과 다른 앱의 권한은 변경하지 않았다. 이어서 일반 창의 타임라인·절차 탭을 바꾸어도 미러링 창 위치가 유지됐으며, `⌃⌘F`로 키오스크의 중앙 배치와 일반 창의 원래 도킹 위치로 복귀하는 것을 실제 화면에서 확인했다.

이후 로컬 설치는 같은 앱 식별자·설치 경로·개발 인증서를 유지한다. 키오스크의 초록 버튼은 별도로 마우스 이벤트만 가로채던 경로를 실제 버튼 동작으로 바꿔, 접근성 도구의 누르기도 같은 키오스크 전환을 수행하도록 수정했다. 최종 설치본의 서명 요구사항이 이전 개발 서명과 같음을 확인한 뒤 교체·재실행했으며, 권한은 유지됐다. 실제 설치 앱에서 초록 버튼을 접근성 도구로 눌러 키오스크 전환과 미러링 창의 중앙 배치를 확인했고, `⌃⌘F`로 일반 창 도킹 상태에 복귀했다.

가져오기로 저장된 검증용 패키지를 로컬 카탈로그에 다시 두고 앱 재시작 없이 새로고침하자, 기존 5개 카드에 데이터가 정의한 여섯 번째 “데이터 연결 확인” 카드와 작업 설명이 표시됐다. 검증 후 테스트 패키지는 실제 카탈로그 밖으로 정리했다. 카드 상세 화면은 화면 제어 도구의 연결 오류로 검증하지 못했으며, 이 결과에 포함하지 않는다.

## 실폰 재생 검증 절차

1. 폰을 잠가 Mac 옆에 두고 `phone state`가 CONNECTED인지 확인한다. 로그인과 인증은 사람이 한다.
2. MCP에서 `read_playbook`으로 대상 앱의 절차와 공통 규칙을 읽는다. 현재 날짜에 유효한 비결제 탐색 흐름을 사용하고 이전 예약 조건을 그대로 실행하지 않는다.
3. `run_combo`에 대상 `app`과 `max_steps: 1`을 전달한다. `phone_screen`으로 실제 화면과 반환 결과를 대조한다.
4. 아는 길이 없으면 그 결과를 기록한다. 비결제 탐색을 한 단계씩 수행해 발자국을 만든 후 같은 시작 화면에서 재생을 확인한다.
5. 정상 경로, 낯선 화면 정지, 사용자 차례 정지를 각각 확인한다. 결제 지점은 자동 탭 없이 멈추는지만 확인하며 이 검증에서 결제 승인을 요청하거나 결제하지 않는다.
6. 각 실행의 시각·앱·걸음 수·정지 이유·기대 결과 일치 여부를 기록한다. 화면 증거는 로컬에만 보관하고 개인정보·예약번호·금액은 공개 문서나 발자국에 옮기지 않는다.
7. 성공한 비결제 경로로 20초 데모를 만든다. 공개 전 화면의 개인정보 노출 여부를 확인한다.

## 이 브랜치(codex/windows-workbench)에서 실행 검증하지 않은 것

- Parallels 창 도킹(작업 화면 전환·자동 맞춤·키오스크 복귀)의 실기 검증. 창 선택은 2026-09-07 실측(App Store 판, 호스트 프로세스가 VM 창 소유)으로 정책 테스트를 고쳤다.
- 대화창(ChatGPT·Codex) 도킹의 실제 최소 크기·접근성 권한·Stage Manager/Spaces 순서·키오스크 복귀(docs/agent-workbench.md).
- Windows 손(windows_*): 캡처·OCR·키·붙여넣기·Win+R·휠·클릭을 2026-09-07 실제 VM(SmartMouse 켠 뒤)에서 확인했다. 등기소의 주소 검색 → 열람 → 결제까지의 전체 경로는 아직 실행하지 않았다.
