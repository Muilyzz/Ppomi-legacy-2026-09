# 공간 자산과 건축물 3D

건축물은 별도 회계 모델이 아니라 같은 자산을 표현하는 공간 자료다. `Accounting/`의 계정·원본 분개·평가 조정은 변경하지 않는다. `Spatial/`은 외곽선 다각형을 입력 높이만큼 압출하는 공통 표현 계층이며, 이름이나 특정 건물별 렌더링 분기가 없다. 부동산 종류를 추가할 때에는 JSON 형상 데이터를 추가한다.

## 사용

기록의 **건축물 3D**에서 로컬 공간 JSON을 가져오거나 전체 자료를 내보낸다. **전체·개인·사업·미분류** 필터와 소유자·사업 ID로 사용 구분을 선택한다. 전체는 자료 목록이며 다른 범위의 금액이나 면적을 합산하지 않는다. **가상 예시 보기**는 데이터 파일을 임시 미리보기하며 저장소에 삽입하지 않는다. **가져오기 예시 저장**으로 JSON 구조를 확인할 수 있다. 예시를 직접 가져오는 경우에도 `isSynthetic: true`와 가상 예시 표시를 유지한다.

외곽선을 드래그해 시점을 회전하고 스크롤로 확대·축소한다. **시점 초기화**로 원래 시점으로 돌아온다. **윤곽선**으로 형상의 면 구조를 확인한다. 화면 폭이 작으면 출처와 치수 패널이 3D 아래로 이동한다. 높이가 낮은 기록 영역은 전체 내용을 스크롤하여 버튼과 자료에 접근하고, 집중 모드에서는 같은 3D 영역이 높이에 맞춰 커진다. 숨겨진 기록 페이지에서는 상호작용과 장면 재생을 멈춘다.

## 데이터 계약

`SpatialData/example.json`이 완전한 스키마 예시다. 모든 JSON 필드는 예시처럼 명시적으로 제공한다.

- 자료: `formatVersion: 1`, `unit: "m"`, `assets`.
- 자산: 불변 `id`, 연결 대상 자산의 안정적인 `entityID`, 표시용 `title`, 이전 미검증 참조인 `accountIDs` 배열, `isSynthetic`, `ownerships`, `usages`, `parts` 배열.
- 형상: 자산 안에서 유일한 `id`, `title`, `footprint`의 `{x, y}` 점 배열, `height`, `elevation`, `provenance`.
- 출처: `kind`는 `measured`(실측), `estimated`(추정), `schematic`(개략). `sourceRecordID`와 치수의 근거를 설명하는 `note`는 필수다.

좌표는 자산 공통 기준의 로컬 수평 좌표이고 높이와 기준면 높이도 미터다. 외곽선은 순서대로 연결한 단순 다각형이며 마지막에 첫 점을 반복하지 않는다. 볼록·오목 다각형과 양쪽 회전 방향을 허용한다. 각 형상은 일정한 수직 높이를 갖는다. 높이가 다른 날개, 단차, 상부 구조는 여러 형상으로 표현한다. 구멍·곡면·기울어진 지붕·BIM 부재는 현재 스키마에 없다.

`height`는 입력 자료가 제공하는 값이다. 층수에서 높이를 자동 생성하지 않는다. 추정 높이를 제공할 때에는 `estimated`와 추정 근거를 입력한다. 치수별 출처가 혼합된 형상은 가장 불확실한 분류를 적용하고 `note`에서 측정된 부분과 추정된 부분을 구분한다. `measured`도 출처가 주장한 분류이며 앱이 측량 정확도를 인증한다는 뜻이 아니다. UI는 색상·문자·출처 ID를 함께 표시한다.

`entityID`는 공간 자료가 설명하는 대상 자산 ID다. 개인·사업 구분을 넣는 용도로 재사용하지 않는다. 이전 `accountIDs`는 이름 그대로 보존하되 UI에 **이전 미검증 참조**라고 표시한다. 신규 `usages.accountLinks`만 아래 규칙으로 검증한다. 형상별 면적은 입력 외곽선에서 계산하며 연면적·실면적·자산가치로 승격하지 않는다. 서로 겹치는 형상의 면적도 자동 합산하지 않는다.

## 개인 소유와 사업 사용

소유와 사용은 서로 다른 출처 기반 기록이다. 개인이 소유한 공간을 사업에 쓸 수 있고, 건물 소유자와 사용 기록의 소유자가 다른 임차 공간도 표현한다. 형상은 하나로 유지하며 사용마다 복제하지 않는다.

- `ownerships`: `ownerID`, 선택적인 `shareBasisPoints`, 소유 근거의 `sourceRecordID`, `note`. 같은 자산에서 같은 소유자 ID를 중복하지 않는다.
- `usages`: 안정적인 `id`, 공통 `scope`, 선택적인 `allocationBasisPoints`, 사용 근거의 `sourceRecordID`, `note`, `accountLinks` 배열. 같은 자산에서 사용 ID와 같은 scope를 중복하지 않는다.
- `scope`: `kind`가 `personal`이면 `ownerID`를 제공하고 `businessID`는 생략한다. `business`이면 `ownerID`와 별도 `businessID`를 제공한다. `unclassified`에는 사업 ID를 부여하지 않는다. 사업 ID는 불투명한 앱 내부 참조이고 사업자등록번호를 읽거나 자동 복사하지 않는다.
- 같은 사업 ID를 서로 다른 사용 기록 소유자에 연결하지 않는다. 공통 `RecordScope.validateConsistency`가 검사한다. 건물 소유자 ID와 사용 기록 소유자 ID가 다르다는 사실 자체는 오류가 아니다.

지분과 사용 비율은 각각 1~10,000 basis points이고, 알려진 비율의 합은 각각 100% 이하다. `null`이나 생략은 **미입력**이며 0%가 아니다. 알려진 일부 합이 100%보다 작아도 나머지를 추정하지 않는다. UI는 소유 지분과 사용 배분, 각각의 출처를 따로 표시한다. 개인·사업 필터는 사용 scope에 적용되고 소유 정보는 독립적으로 표시한다.

이전 JSON에 `ownerships` 또는 `usages`가 없으면 빈 배열로 읽는다. 사용 정보가 없는 자료는 전체/미분류에서만 보이며 개인 소유나 사업 사용을 추론하지 않는다. 기존 파일을 읽거나 같은 내용을 재시도할 때 새 필드로 덮어쓰지 않는다. 구분을 추가하는 수정본은 새 공간 자료 ID로 가져온다.

## 검증된 장부 연결

새 `accountLinks`는 `{ "bookID": "...", "accountID": "..." }` 형식이다. `SpatialAccountingLinks`가 별도 경계에서 다음을 검증한다.

1. 해당 장부와 계정이 회계 저장소에 등록되어 있다.
2. 계정의 `bookID`가 지정한 장부와 같고 계정 종류가 `asset`이다.
3. 사용 scope와 장부의 `effectiveScope`가 개인·사업·소유자·사업 ID까지 정확히 같다.
4. 미분류 사용에는 검증된 계정 연결을 등록하지 않는다.

`SpatialGeometry`에는 회계 DB 의존성이 없다. `SpatialStore`는 새 `accountLinks`가 있는 경우에만 주입 가능한 `accountingSnapshot`을 읽고, 가져오기와 snapshot 모두에서 검증한다. 연결 검증은 계정·분개·금액을 생성하지 않는다. 출처, 링크, 비율을 추가하는 것으로 자산 취득이나 비용 배분 분개를 만들어 내지 않는다.

사업 ID와 기록 주체의 일관성은 각 저장소 내부에서 검증한다. 저장소 사이에는 실제 등록된 링크의 대상 장부·계정·scope만 비교하며, 서로 연결하지 않은 사업 ID를 전역 사업 명부처럼 자동 통합하지 않는다. 회계 저장소는 공간 저장소를 역으로 읽지 않으므로 순환 잠금도 만들지 않는다. 따라서 연결하지 않은 공간 사용과 별개로 추가한 회계 장부가 같은 사업 ID 문자열을 사용하더라도 기존의 다른 유효한 공간 링크를 무효화하지 않는다.

가상 예시 v2는 한 개인의 소유와 같은 공간의 개인 40%·사업 60% 사용을 보여준다. `accountLinks`는 비어 있어 단독 미리보기에 회계 자료를 삽입하거나 읽을 필요가 없다. 예시의 비율은 설명용 데이터이며 실제 자료의 기본 배분이 아니다.

## 저장과 검증

자료는 `~/Library/Application Support/Ppomi/Private/spatial-assets.json`에 저장한다. 디렉터리는 0700, 자료는 0600 권한이고 프로세스 간 파일 잠금 뒤 검증·병합·원자 쓰기를 수행한다. 원본과 같은 ID의 같은 데이터는 재시도 가능한 무변경 가져오기다. 같은 ID의 다른 데이터는 전체 가져오기를 거부한다. 수정본은 새 공간 자료 ID를 부여하고 동일한 `entityID`에 연결한다. 선택 UI에 두 버전이 남는다.

가져오기는 사용자가 선택한 일반 로컬 JSON 파일만 허용한다. URL, 외부 3D 모델, 스크립트, 네트워크 로딩은 없다. 최대 파일 8MB, 자산 100개, 자산당 형상 100개, 형상당 점 256개, 전체 점 20,000개다. 좌표·높이는 유한해야 하고 외곽선 중복·자기교차·접촉·겹침·면적 없는 도형은 거부한다. 잘못된 가져오기로 저장된 자료를 변경하지 않는다.

## 렌더러 경계와 검증

`SpatialSceneView.swift`만 SceneKit에 의존한다. [SCNShape](https://developer.apple.com/documentation/scenekit/scnshape/extrusiondepth)의 중심 압출을 수직으로 회전하고 기준면 높이를 보정하며, [SCNView 카메라 제어](https://developer.apple.com/documentation/scenekit/scnview/allowscameracontrol)를 사용한다. 원점에서 멀리 있는 좌표는 표시 직전에 중심으로 이동하여 정밀도를 보존한다. 원본 데이터는 바꾸지 않는다.

[Apple 문서](https://developer.apple.com/documentation/realitykit/bringing-your-scenekit-projects-to-realitykit)에 따르면 SceneKit은 macOS 26부터 soft-deprecated이며 여전히 사용 가능하다. 이 범위의 압출과 기본 카메라 조작은 SceneKit으로 격리 구현했고, 향후 RealityKit으로 교체해도 공간 자료나 회계 엔진은 바꿀 필요가 없다.

`SpatialAssetTests`는 출처·좌표 보존, 오목 다각형과 좌표 방향, 퇴화·자기교차·접촉 검증, 단위·ID·누락 값·비유한 값 거부, 예시 미삽입, 불변 ID 충돌의 원자성, 권한, 동시 가져오기, 입력 크기 제한, 장면 압출 높이·기준면 배치를 검증한다. `SpatialScopeTests`는 이전 JSON 미분류 보존, 부분/미입력 비율, 같은 형상의 개인·사업 필터, 개인 소유와 사업 사용의 분리, 다른 scope·장부·비자산 계정 거부, 검증 실패의 원자성, snapshot의 링크 재검증을 검증한다.
