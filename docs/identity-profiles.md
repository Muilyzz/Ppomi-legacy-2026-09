# 자동입력 기본정보 프로필

이름·생년월일·휴대폰 번호·통신사·사업자 상호·사업자등록번호와 은행별 통장 고객명·출금계좌번호를 한 번 등록하고, 사용자가 허용한 양식의 기본정보 입력에 재사용한다. 비밀번호·주민등록번호·인증번호·카드번호는 등록 대상이 아니다. 기본정보를 입력하는 기능이며 로그인이나 본인 인증 자체를 대신하지 않는다.

## 등록과 확인

대화에서 **“내 기본정보를 뽀미에 등록해줘”**라고 요청하면 에이전트가 필요한 항목을 확인하고 `profile_save`로 저장한다. 사용자가 직접 제공하며 등록·수정을 요청한 정보만 사용한다. 웹페이지나 OCR에서 발견한 이름·번호를 프로필에 옮기지 않는다.

대화에 보낸 내용과 도구 입력은 호스트의 대화 기록에 남을 수 있다. 대화 기록에 남기고 싶지 않으면 뽀미 설정의 **자동입력 기본정보 → 프로필 추가**에서 직접 등록한다. 목록에는 마스킹한 요약이 표시되며, **보기·편집**을 열었을 때 전체 값을 확인하고 수정할 수 있다. 입력 중인 변경은 메모리에만 두고 **저장**을 눌렀을 때 반영한다. 편집 화면에서 프로필 삭제도 가능하다.

대화 등 다른 프로세스에서 저장한 변경은 앱 활성화 시 다시 읽는다. 설정의 **새로고침**으로도 갱신할 수 있다. 키체인 잠김·접근 거절·유효하지 않은 값 등 오류는 화면과 도구 응답에 표시하며 다른 저장소로 우회하지 않는다. 장부의 ‘내 이름’을 자동입력 기본정보로 복사하지 않는다.

## 가족별 구분

본인의 기본 `profile_id`는 `self`다. 다른 가족에게는 별도 ID를 쓰고, `label`에는 실제 이름 대신 가족을 구분할 호칭을 사용할 수 있다. 상태 응답에는 ID와 구분 이름의 첫 글자만 남긴 `label_hint`가 포함된다. 저장된 개인·사업자 정보 원문은 상태 응답에 포함하지 않는다. 현재 프로필 하나에는 개인 기본정보와 사업자 정보 한 쌍을 저장한다. 이는 같은 Mac에서 값을 구분하는 기능이며 가족별 접근 권한을 분리하는 계정 시스템은 아니다.

프로필 ID는 영문 소문자로 시작하는 1~48자의 영문 소문자·숫자·밑줄·하이픈이며, 10자리 이상 연속된 숫자를 포함할 수 없다. 추가 프로필은 설정에서도 생성할 수 있다. 다른 가족의 프로필이나 이미 로그인한 계정을 이번 당사자의 기본값으로 삼지 않는다. 세션에서 정한 당사자와 사용할 프로필을 확인하고, 모호할 때만 구분을 요청한다.

## MCP 도구

다음은 값이 없는 입력 스키마다. 실제 이름·날짜·전화번호를 공개 문서나 실행 예시에 넣지 않는다.

```text
profile_save({
  profile_id?: string,   // 기본 self
  label?: string,
  name?: string,
  birth_date?: string,   // YYYY-MM-DD
  phone?: string,        // 010으로 시작하는 11자리
  carrier?: string,      // skt | kt | lgu | skt_mvno | kt_mvno | lgu_mvno
  business_name?: string,
  business_registration_number?: string // 숫자 10자리 또는 3-2-5 표시형식
})

profile_status({ profile_id?: string })
profile_delete({ profile_id: string })

profile_fill({
  profile_id?: string,   // 기본 self, 다른 가족은 명시
  form: "eais_pass" | "eais_business" | "kb_id_lookup",
  bank_id?: "kb",       // kb_id_lookup에서 필수, 다른 양식에서는 금지
  field: "name" | "birth_date" | "phone" | "carrier" | "business_name" | "business_registration_number" | "bank_customer_name" | "bank_account_number",
  segment?: 1 | 2 | 3,   // 사업자등록번호에만 필수. 앞 3자리·가운데 2자리·뒤 5자리
  x: number,            // 최신 화면 입력칸 중심의 가로 비율, 0~1
  y: number             // 최신 화면 입력칸 중심의 세로 비율, 0~1
})
```

| 도구 | 처리와 응답 |
|---|---|
| `profile_save` | 사용자가 등록·수정하려는 항목을 저장한다. 생략한 항목은 기존 값을 유지하고 빈 문자열은 그 항목을 비운다. 저장 여부와 항목별 등록 여부를 반환한다. |
| `profile_status` | ID를 생략하면 프로필 목록을, 지정하면 해당 프로필의 ID·마스킹한 `label_hint`·항목별 등록 여부를 반환한다. 개인·사업자 정보 원문은 반환하지 않는다. |
| `profile_delete` | 사용자가 삭제를 요청한 프로필 하나를 지운다. 반드시 ID를 지정한다. |
| `profile_fill` | 등록된 항목 하나를 지원 양식에 입력한다. 읽을 수 있는 항목은 로컬 화면으로 값 일치를 확인한다. 마스킹된 사업자번호 칸은 `input_attempted`, `value_verified: false`, `requires_site_verification`으로 범위를 구분하며 입력 원문은 반환하지 않는다. |

생년월일은 실제 날짜인지 검사하며 미래 날짜를 받지 않는다. 전화번호는 일반적인 구분 기호를 정리한 뒤 010으로 시작하는 11자리인지 검사한다. 통신사 값은 위 여섯 가지를 지원한다. 일부 항목만 등록할 수도 있으며, 없는 항목의 입력 요청은 이유를 알리고 멈춘다.

사업자번호는 ASCII 숫자 10자리 또는 정확한 3-2-5 표시형식을 받아 구분 기호 없는 숫자로 저장한다. 번호를 추정·보정하지 않으며 형식 검사와 저장 성공은 사업자 실재, 상태, 상호 일치, 사이트 가입 가능 여부의 검증이 아니다. 해당 사이트의 실제 결과를 별도로 확인한다. 사업자 정보가 없던 기존 키체인 프로필도 그대로 읽을 수 있다.

## 뽀미 Mac 채팅의 질문 카드

뽀미 자체 채팅 에이전트는 `request_user_input`으로 선택지·자유 입력·제출·취소가 있는 질문 카드를 표시한다. 일반 질문의 답은 모델 도구 결과로 돌아간다. 다른 호스트의 질문창을 뽀미로 그대로 전달하는 기능은 아니다.

은행 정보는 별도 `request_bank_profile(profile_id, bank_id: "kb")` 카드에서 등록한다. 기존 고객명·계좌번호는 등록 여부만 조회하고 미등록 항목만 묻는다. 입력값은 카드의 입력칸에서 로컬 네이티브 브리지로 직접 보내 키체인에 저장한다. 모델 도구 인자·답변·일반 채팅·메모리에는 원문을 넣지 않고 등록 상태만 반환한다. 이미 저장된 값은 설정에서 수정한다. 고객명을 기존 이름·상호에서 추측하거나 조합하지 않는다.

은행 카드는 활성 채팅 세션에서 만든 일회용 요청에만 제출할 수 있다. 화면의 답변 대기는 5분이며 네이티브 제출 토큰은 최대 10분 뒤 만료된다. 취소·세션 종료 시 요청을 폐기한다. 요청 당시 누락 항목을 모두 입력해야 저장하며, 그 사이 설정에서 등록된 항목을 오래된 카드가 덮어쓰지 않는다. 유효성 검사나 키체인 접근 실패는 원문 없는 오류로 알린다. 비밀번호·OTP·주민번호를 위한 입력칸은 없다.

은행 정보는 `IdentityProfile.bankProfiles[bank_id]`에 별도로 둔다. `customer_name`과 `account_number`만 허용하며, 계좌번호의 공백·하이픈을 제거한 ASCII 숫자 6~20자와 고객명 길이 등을 검사한다. 이 검사는 은행 계좌의 실재·소유·업무 귀속을 입증하지 않는다. `profile_status`의 `bank_profiles`는 은행 ID와 두 항목의 등록 여부만 반환한다. 일반 `profile_save`는 은행 원문을 받지 않고 기존 은행 정보를 보존한다. 기존 프로필도 그대로 읽을 수 있다.

## KB 개인사업자 ID 조회

`kb_id_lookup`은 확인된 공식 팝업 `https://obiz.kbstar.com/quics?page=C019750`의 개인사업자 양식만 지원한다. `bank_id: "kb"`와 `bank_customer_name`, `birth_date`, `bank_account_number` 중 하나를 지정한다. 통장 고객명·출금계좌번호는 해당 은행 프로필에서, 생년월일은 기존 개인 프로필에서 읽어 화면의 YYMMDD 형식으로 변환한다.

입력 직전 로컬 OCR로 주소창의 정확한 호스트·경로·단일 page 값, ID 조회 제목, 개인사업자 생년월일 예시, 라벨과 입력 행의 상대 배치 및 포커스를 확인한다. 법인사업자·다른 페이지·겹친 보안 입력 화면·비밀번호나 확인 버튼 좌표는 거절한다. 키체인 값은 기존 비공개 입력·검증 경로 안에서만 사용하고 결과는 상태로 반환한다. 입력 검증은 ID 조회 또는 인증 성공을 뜻하지 않으며, 계좌 비밀번호 입력과 조회 인증은 공식 화면에서 당사자가 수행한다.

이 어댑터는 현재 관측된 Windows OCR 양식에 한정된다. Parallels 게스트 DOM 연동이나 KB 발급 본문·다른 은행·법인사업자 폼을 지원한다고 보장하지 않는다. 실제 은행 값 입력 및 ID 조회는 아직 검증하지 않았다.

## 첫 지원 양식: 세움터 통신사PASS

`profile_fill`의 첫 지원 대상은 Parallels Windows의 세움터 간편인증 **통신사PASS** 기본정보 양식(`eais_pass`)이다. Mac 브라우저의 임의 폼이나 다른 인증 제공자에 범용으로 입력하는 도구가 아니다.

1. 세움터 로그인에서 사용자가 선택한 간편인증 제공자를 현재 화면에서 찾는다. 제공자 순서는 창을 다시 열 때 바뀔 수 있으므로 과거 순번·좌표를 재사용하지 않는다. 통신사PASS를 삼성패스와 구분하고, `통신사PASS` 헤더·선택 테두리·통신사 필드로 선택을 확인한다.
2. 사용할 프로필의 등록 여부를 확인한다. 아직 등록되지 않은 항목은 사용자의 등록 요청과 제공 정보에 따라 먼저 저장하거나 설정에서 직접 등록하도록 안내한다.
3. 최신 화면에서 필요한 항목의 입력칸 중심 `x`, `y`를 확인하여 한 항목씩 요청한다. 입력기는 주소창의 세움터 주소, 통신사PASS 양식, 항목 라벨과 입력 위치를 로컬 OCR로 다시 검증한다. 일치하지 않거나 화면이 바뀌면 입력을 중단한다.
4. `name`은 이름 칸, `birth_date`는 생년월일 칸을 가리킨다. 날짜는 양식에 맞춰 구분 기호 없는 숫자로 입력한다. `phone`은 고정된 **010 뒤의 8자리 입력칸**, `carrier`는 **통신사 드롭다운**을 가리킨다. 통신사는 등록 값에 맞는 메뉴 항목을 현재 화면에서 찾아 선택한다.
5. 로컬 화면에서 해당 항목의 반영 여부를 확인하고 상태만 반환한다. 확인이 안 되면 자동으로 같은 값을 반복 입력하지 않는다. 기본정보 입력 후 **약관 동의·인증요청·휴대폰 PASS 승인**은 당사자가 직접 수행한다. 사용자 완료 후 인증·로그인 결과를 확인하고 원래 도면 작업을 이어간다.

현재 주소·라벨·배치에 대한 검증 조건을 만족하지 않는 창 크기나 변경된 UI에서는 중단할 수 있다. 항목 입력 검증은 로그인 성공이나 도면 발급 성공을 뜻하지 않는다.

## 사업자 지원 양식: 세움터 사업자인증

`eais_business`는 세움터 사업자회원의 사업자인증 페이지(`/moct/awp/aba01/AWPABA01F04`)를 대상으로 한다. `business_name`은 상호 칸, `business_registration_number`는 `segment` 1·2·3으로 지정한 번호 칸에 입력한다. 에이전트는 번호 원문을 조회하거나 직접 세 부분으로 나누지 않고 저장된 프로필과 현재 입력칸의 위치만 전달한다.

번호 칸을 가르는 두 구분 기호와 라벨·현재 포커스가 확인되지 않으면 입력을 중단한다. 폼 아래 주민등록번호 오용에 대한 안내문은 별도 입력 항목으로 취급하지 않는다. 입력기는 처리동의·공동인증 버튼을 누르지 않는다. 호스트 에이전트가 현재 사용자 허용 범위에 맞게 필요한 준비를 이어가며, 인증서 비밀번호는 사람이 직접 입력한다. 필수 약관 동의가 이미 확인됐다면 같은 동의를 다시 요청하지 않는다.

2026-09-08 [세움터 사업자인증 화면의 공식 스크립트](https://www.eais.go.kr/_nuxt/c5f9883.js)를 확인한 결과, 번호 칸의 키 검사는 Ctrl·A·V를 허용하지 않는다. Ctrl+A·붙여넣기 실패를 Parallels의 modifier 전달 실패로 단정하지 않는다. 첫 칸은 일반 텍스트, 뒤 두 칸은 사업자번호를 가리는 `password` 타입이다. 뒤 두 칸에서 마스킹 기호나 길이를 확인하는 것은 원문 일치 검증이 아니며 실제 인증 성공은 사이트 결과로 따로 확인해야 한다. 마스킹된 기존 내용의 출처가 불명확하면 같은 값을 자동으로 반복 입력하지 않는다.

2026-09-08 실기에서 사업자회원 약관 화면의 필수 두 항목에 대한 사용자 동의 후, 선택 항목을 제외하고 사업자인증 페이지에 진입한 것을 확인했다. 현재 확인한 필드는 사업자명·등록번호 세 칸·등록번호 처리 동의이며 다음 행동은 공동인증이다. 새 사업자 프로필 기능의 실제 저장·입력·가입 결과는 설치 후 별도로 검증한다.

## 저장과 입력의 범위

프로필 전체 값은 macOS의 기본 키체인(통상 로그인 키체인)의 암호화된 항목에 저장한다. 호출 앱을 신뢰 대상으로 하는 앱 ACL을 지정하며 iCloud 키체인 동기화는 사용하지 않는다. 파일·DB·AppSettings에 별도 사본을 저장하지 않는다. 화면 잠금만으로 접근이 항상 자동 차단되거나 `ThisDeviceOnly`로 보호된다고 보장하는 방식은 아니다.

전용 `profile_fill` 경로는 입력값을 일반 동작 발자국·OCR 장부·지속 캡처에 남기지 않는다. 확인용 PNG는 접근 권한을 제한한 로컬 임시 폴더에 만들고 OCR·포커스 검증 후 삭제하며, OCR 결과는 메모리에서만 처리한다. 에이전트에 개인 원문을 반환하지 않는다. 이 범위는 전용 경로의 동작 설명이며, 입력 후 다른 도구로 별도 화면을 수집하거나 호스트가 대화 내용을 저장하는 것까지 차단하는 기능은 아니다.

Windows의 비공개 텍스트 입력은 원문을 프로세스 인자나 로그에 넣지 않고 표준입력(`stdin`)으로 전달한다. 일반 텍스트 경로는 붙여넣기 후 클립보드가 뽀미가 넣은 상태 그대로일 때만 이전 Mac 클립보드를 복원하며, 사용자가 새로 복사한 내용은 덮지 않는다. **Windows 클립보드 기록까지 삭제된다고 보장하지는 않는다.** 사업자번호 칸에는 `type-digits-private`가 ASCII 숫자 1~10자만 받아 Home·Delete와 숫자키를 보낸다. 이 경로는 클립보드나 Ctrl 단축키를 사용하지 않는다. 실제 입력칸의 빈 상태와 포커스를 확인하지 못하면 값을 보내지 않는다. 일반 텍스트 입력의 성공을 숫자 경로의 성공으로 간주하지 않는다.

실제 사용자 프로필의 저장·Windows 자동입력·인증 성공 여부는 각각 실기 결과를 확인한 뒤 기록한다. 코드와 안내 추가만으로 그 단계들을 완료했다고 보고하지 않는다.

## 실제 검증 상태

2026-09-08, 합성 정보로 키체인 항목의 생성·읽기·수정·삭제를 검증했으며, 사용자가 등록을 요청한 기본정보의 실제 MCP `profile_save` 저장도 성공했다. 세움터 통신사PASS에서는 `profile_fill`의 통신사 메뉴 선택과 해당 필드의 반영을 확인했다.

이름 입력 시도에서는 입력칸 포커스 검증을 통과했지만 실제 글자가 반영되지 않아 결과 검증이 실패했다. 후속 시도는 포커스 증거를 확인하지 못해 값 전송 전에 차단되었다. 이름·생년월일·휴대폰 번호의 실제 텍스트 자동입력은 아직 검증하지 못했다. 약관 동의·인증요청·휴대폰 PASS 인증·로그인 완료도 확인하지 않았다. 저장 성공과 통신사 선택 성공을 전체 자동입력 또는 인증 완료로 기록하지 않는다.

설치본의 MCP 전체 프로필 목록 조회와 설정의 마스킹 목록 표시도 실기에서 확인했다. 목록 조회에서 발생하던 오류는 비밀번호 항목의 전체 열거와 데이터 반환을 한 요청으로 결합한 것이 원인이었다. 해당 서비스의 계정 메타데이터를 먼저 열거하고 계정별로 데이터를 읽도록 수정했으며, 저장된 프로필은 보존했다.

## 2026-09-08 검증 범위 수정

- 보호 대상 낱말(비밀번호·인증번호·주민번호 등) 차단은 PASS 양식 패널 안에서만 적용한다. 패널은 ‘본인인증 정보 입력’ 제목의 글자 높이를 단위로 잡은 고정 상자다. 모달 옆에 남아 있는 로그인 페이지의 “아이디와 비밀번호를 이용” 문구 때문에 실제 기본정보 양식이 거절되던 문제를 고쳤다. 패널 안의 보호 대상 입력 차단은 그대로다.
- 주소창 증거는 화면 상단 15% 고정 비율 대신 “선택된 통신사PASS 헤더보다 위, 창 상단 1/3 안”으로 판단한다. Parallels 창이 824×517처럼 작아지면 브라우저 크롬이 상단 17%까지 내려와 기존 고정 비율에서 검증이 실패했다. 페이지 본문에 적힌 도메인은 여전히 증거가 아니다.
- Windows 키 입력이 “간헐적으로” 실패하던 원인은 입력 경로가 아니라 설치본 helper `phone`의 서명 식별자였다. `com.muilyzz.ppomi.phone`으로 따로 서명된 helper는 TCC가 별개 앱으로 보아 키보드 이벤트 게시를 조용히 거절한다(마우스 클릭은 통과해 증상이 헷갈린다). 저장소의 서명 없는 바이너리와 앱 식별자 `com.muilyzz.ppomi`로 서명한 사본은 같은 소스로 키가 들어가는 것을 Win+R 실행창으로 확인했다. `scripts/make-app.sh`의 로컬 서명은 helper를 앱 식별자로 서명한다. 다만 같은 바이너리도 `뽀미.app/Contents/MacOS/` 안에서 실행되면 여전히 키가 버려지고(앱 번들로 귀속), 번들 밖으로 복사한 사본은 키가 들어간다. 그래서 `Collect/Phone.swift`는 번들 helper를 `~/Library/Application Support/Ppomi/phone`으로 복사해 그곳에서 실행한다(번들 사본이 더 새로우면 갱신). 배포용(Developer ID) 서명은 아직 helper 식별자를 지정하지 않으므로 같은 점검이 필요하다.

## 후속 실기: PASS 기본정보 입력 확인

설치본의 stdio MCP `profile_fill`로 이름·생년월일·휴대폰을 실제 입력했다. 생년월일과 휴대폰은 즉시 `verified: true`, 이름은 입력 직후 OCR 검증이 한 차례 실패했으나 다른 필드로 포커스가 옮겨진 뒤 조회에서 `already_filled: true, verified: true`를 반환했다. 재조회는 이름을 재입력하지 않았다. 화면에서도 세 값과 기존 통신사 선택이 등록한 프로필과 일치함을 확인했다. 입력값 원문은 이 기록에 남기지 않는다.

검증 시 약관은 미동의이고 인증 요청은 전송하지 않았다. 기본정보 자동입력의 성공이며 PASS 인증·세움터 로그인·도면 수집 성공을 뜻하지 않는다. 입력 직후 이름 OCR의 일시적인 실패 응답은 후속 개선 대상으로 남는다.
