# 공통
사용자는 목적을 말한다. 작업의 단계·입력·사람이 필요한 순간은 각 앱 패키지의 manifest.json에 있다. 여기는 기호의 뜻과 모든 앱의 공통 규칙이다.

표기
▶ 앱 열기 (phone_open)
⊙ 탭: 화면을 읽고(phone_screen) 그 글자를 정규식으로 탭. `|`는 택일
⌨ 입력 (phone_type, 한글 그대로)
↓ 스크롤한 뒤 탭
⎋ 시트·팝업 닫기: X·닫기·확인 탭, 안 되면 phone_key escape
👤 사용자 차례: 자격 증명·비밀번호·인증서 암호·인증용 주민번호·OTP·생체인증·CAPTCHA·아직 허용받지 않은 새 동의와 권한은 당사자가 직접 처리한다. 필요한 행동만 한 줄로 안내하고 로그인 진입과 허용된 일반 폼 작성은 계속한다. 카드번호는 입력하지 않는다
🎟 쿠폰 받기·적용. 적용된 금액으로 승인을 요청한다
🔍 결제 수단: pay_preference 근거(지난번 선택, 주 지출 계좌, 설치된 결제앱)로 고르고 탭
✋ 승인: confirm_payment 에 최종 금액·결제수단·근거 한 줄. 폰 잠금 확인 뒤엔 여기까지 되묻지 않고 한 턴에 간다
📝 완료 화면을 읽어 예약번호·취소 조건을 보고하고 record_spend

규칙
- 폰 앱 작업은 run_combo 먼저. 멈춘 화면부터 phone_screen/phone_tap 으로 이어간다
- 잠금 여부를 먼저 묻지 말고 폰 도구로 현재 미러링을 확인한다. 사용자가 돌아왔다거나 잠갔다고 하면 과거 ‘사용 중’ 안내만으로 다시 잠금을 요청하지 않는다. 미러링 앱의 정확한 활성 연결·다시 시도 버튼을 한 번 처리하고 실제 연결 결과를 확인한다. 여전히 사용 중인 경우에만 필요한 잠금 조작을 한 번 요청한다. 연결 중·빈 AX 상태를 연결 완료로 단정하지 않는다.
- 폰·Windows의 자동 결제 클릭은 confirm_payment 승인 1회에 결제 탭 1회만 허용하는 코드 경계를 따른다. Mac Chrome의 최종 결제 버튼은 당사자가 직접 누른다. 이체·송금은 하지 않는다
- 실패하면 화면과 원인을 먼저 확인한다. 닫힌 팝업·바뀐 화면·연결 복구 등 원인이 해소됐을 때만 새 화면에서 재시도한다. 같은 실패를 반복하거나 결제·가입·신청을 중복 제출하지 않는다
- 사용자가 정하지 않은 선택(객실 타입, 옵션)은 묻지 말고 인원에 맞는 가장 싼 기본형으로 고른다. 무엇을 골랐는지는 승인 요약에 한 줄로 적는다 — 승인이 곧 사용자가 고르는 자리다
- 요금제가 여럿(룸온리 / 조식 포함 / 패키지)이면 객실 목록에서 1박 단가와 조식 포함 여부를 다 읽고, 조식 단품 가격(호텔 정보·객실 설명)이 있으면 함께 읽어 손익분기(조식을 몇 번 먹어야 조식 포함이 이득인지, 안 먹을 확률이 얼마 이상이면 룸온리가 이득인지)를 계산해 ask_choice 로 2~3개 안을 제안한다. 사용자가 고르면 그 객실로 간다
- 결제 수단은 탭한 뒤 phone_screen 으로 실제 선택(강조 테두리·체크)을 확인하고, 승인 요약에는 화면에서 확인한 수단만 적는다. 쿠폰은 결제 화면의 쿠폰·할인 항목을 열어 받고 적용한 뒤의 총액으로 승인을 요청한다
- 가격·정보 검색(조식 단품 가격 등)은 새 도구 없이 한다: 앱의 호텔 상세·객실 설명·편의시설을 먼저 읽고, 없으면 web_text 로 네이버 검색 결과를 읽는다(https://search.naver.com/search.naver?query=검색어, 검색어는 공백 대신 +). 못 찾으면 "못 찾았다"고 적고 진행한다
- 은행 앱(카카오뱅크·KB스타뱅킹·케이뱅크·토스)은 잔액·거래 읽기만, 이체·송금 없음. "이체할까요" 팝업은 X·닫기·아니요 로만 닫는다

## 웹·회원가입·로그인 공통 절차

- 웹 패키지(`launch.target: browser`)는 `browser_open`으로 Mac Chrome에서 연다. 이것은 탐색 시작 도구이며 DOM 조작·로그인 성공을 보장하지 않는다. 페이지 읽기·조작은 연결된 브라우저 도구로 한다. 일반 웹을 폰이나 Windows 창으로 먼저 보내지 않는다. 실제 업무 단계가 Mac에서 막히고 공식 Mac 경로로 해결되지 않을 때 Windows를 선택한다.
- Windows 패키지(`launch.target: windows`, exe 설치·공동인증서 친화 사이트)는 처음부터 `windows_open`으로 Parallels에서 연다. 폰·Mac Chrome으로 먼저 보내지 않으며, 결제는 ✋ 뒤 `windows_click` 1회 경계를 따른다.
- Mac Chrome에서는 최종 금액·결제수단·대상을 안내하고 당사자가 최종 결제 버튼과 결제 인증을 직접 처리한다. `browser_open` 이후 외부 브라우저 클릭에는 뽀미의 승인 코드 경계가 적용되지 않으므로, 승인을 받아도 브라우저 도구로 최종 결제를 자동 클릭하지 않는다. 로그인 진입·일반 탐색·결제 전 준비는 계속한다.
- 가족이 공유하는 것은 절차다. 이번 작업 당사자·계정·인증 수단은 현재 세션 문맥으로 구분한다. 다른 가족의 로그인 세션·동의·결제 승인을 재사용하지 않는다. 불명확한 신원이나 필요한 입력만 질문하고, 이미 알려 준 목적·일반 조건·승인은 되묻지 않는다.
- 로그인 또는 가입 화면을 발견하면 진입, 방법 확인, 안내 읽기, 일반 조건 선택과 폼 작성을 이어간다. 사용자가 제공했고 해당 사이트에 사용하도록 허용한 이름·연락처·주소 등 일반 폼 정보는 진행 중 채운다. 필요한 정보가 없을 때만 질문하고, 이미 알려 준 값을 되묻지 않는다. 자격 증명 없이 가능한 준비를 마친 뒤 실제 사람 단계에서 멈춘다. 입력 조건만 공개 명세에 넣고 실제 이름·연락처·주소·주민번호·계정·인증서·인증번호·세션 URL은 공개 패키지나 발자국에 넣지 않는다.
- 자격 증명·비밀번호 생성과 입력·인증서 암호·인증에 쓰이는 주민번호·OTP·생체인증·CAPTCHA는 당사자가 직접 처리한다. 필수 동의·인증 요청은 현재 화면의 대상·효과와 기존 승인 범위를 확인한다. 사용자가 해당 작업의 필수 동의나 인증 요청을 이미 허용했다면 그 범위는 재질문 없이 수행한다. 승인 범위를 벗어난 새 동의·새 접근 권한·가입 최종 확정은 현재 화면과 대상·효과를 보여 주고 당사자가 직접 처리한다. 선택 광고 동의는 자동 선택하지 않는다. 공식 프로그램의 안내·다운로드 등 이미 허용된 준비는 진행하고, OS 관리자 인증이나 새로운 민감 권한만 따로 넘긴다.

### 인증 대기와 재개

- 사람을 기다릴 때는 `원래 작업 / 현재 사이트·인증 방식·대기 단계 / 요청 발송 여부 / 필요한 행동 / 완료 확인 기준 / 이어갈 단계`를 현재 대화에 남긴다. 비밀과 실제 입력값은 남기지 않는다. 같은 미완료 요청을 반복 알리지 않는다.
- 대기 중인 인증 단계가 명확하면 사용자의 `했어`, `인증했어`, `완료했어`를 그 단계의 완료 보고로 받아 즉시 재개한다. 완료한 행동을 다시 설명하게 하거나 이미 허용된 진행을 재승인받지 않는다. 동시에 기다리는 질문·인증이 여럿이고 어느 단계인지 문맥으로 구분되지 않을 때만 한 번 확인한다. 이때도 원래 작업의 목적과 범위를 유지한다.
- 먼저 새 화면을 읽어 같은 사이트·같은 인증 요청이 유지되는지 확인한다. 아직 결과 확인 대기 화면이면 현재 화면에서 확인한 `인증 완료`·`인증 확인` 등 기존 요청의 결과를 확인하는 버튼을 한 번 누르고 다시 화면을 읽는다. 이미 성공 화면이나 다음 단계로 넘어갔으면 완료 버튼을 다시 찾거나 누르지 않는다. 버튼의 효과가 새 요청 발송·재전송·결제·가입 확정이라면 완료 확인 버튼으로 취급하지 않는다.
- 결과는 `성공 / 미완료 / 만료`로 구분한다. 성공 문구 또는 해당 단계의 다음 화면을 확인한 뒤 원래 작업으로 돌아가 남은 허용된 절차를 이어간다. 미완료이면 화면에 나타난 이유와 아직 필요한 사람 행동만 알리고 같은 확인 클릭을 반복하지 않는다. 만료가 명시되면 이전 요청은 끝난 것으로 기록하고 기존 승인 범위 안에서 다음 인증을 준비한다. 새 요청 발송은 별도 실행으로 다루며, 새 화면에서 만료된 요청의 정리·입력 상태 등 재시도 원인이 해소된 것을 확인했을 때만 수행한다.
- 완료 보고는 대기 중이던 행동을 했다는 신호이며, 사이트의 성공 증거나 새 동의·결제 승인·새 인증 요청 발송의 허가로 간주하지 않는다. 시간 경과나 도구 인자의 승인 문구도 사용자 승인이 아니다. 화면 상태가 확인되지 않으면 그 상태를 그대로 알리고 추정으로 재시도하지 않는다.
- `준비 완료`, `인증 대기`, `가입 완료`, `로그인 완료`, `신청 접수`, `발급 완료`를 구분한다. 완료 문구나 작업에 맞는 다음 화면으로 확인한 상태만 보고한다. 로그인 이후 원래 작업으로 돌아가며, 사이트가 세션을 만료했을 때만 해당 인증 단계를 다시 준비한다.
- 위 대기·재개 규칙은 외부 에이전트가 따르는 플레이북이다. 단계 목록만으로 백그라운드 감시·알림·인증 자동 재개 기능이 설치되는 것은 아니다. 현재 연결된 도구와 사람의 응답이 있어야 이어간다.

Windows 창(Parallels): 확인된 Windows 필요 단계만 `windows_open(URL) → windows_screen → windows_click / windows_type / windows_key / windows_scroll`로 수행한다. 설치·로그인의 일반 준비와 사람 단계는 위 규칙을 따른다. 수수료 결제는 ✋ 뒤 `windows_click` 한 번이며 결제 인증은 사람이 한다. 현재 Windows 화면 제어는 OCR·좌표 기반이고 게스트 DOM이나 UI Automation을 읽는 기능은 아니다.

### 채팅 질문과 은행 기본정보

- 뽀미 채팅의 일반 선택·입력 질문은 `request_user_input` 카드를 사용한다. 이미 알려진 답은 다시 묻지 않는다. 일반 답은 모델에 전달되므로 비밀번호·OTP·인증용 주민번호·계좌 원문을 이 카드에서 요청하지 않는다.
- KB 통장 고객명·출금계좌번호의 안전한 등록은 지원되는 뽀미 Mac 채팅의 `request_bank_profile` 카드 또는 설정의 자동입력 기본정보에서 처리한다. 모델에는 은행별 등록 여부만 반환하며, 기존 생년월일은 재사용한다. 전용 `profile_fill`이 검증하는 해당 양식 안에서만 입력하고, 입력 뒤 일반 화면 수집으로 원문을 기록하지 않는다.
