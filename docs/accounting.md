# 범용 분개장

새 사례는 계정과목과 분개 데이터로 추가한다. 학습·운동·구독·식사별 모델, 분개 함수, 화면을 늘리지 않는다. 공통 엔진은 장부, 단위, 계정 참조, 차변·대변, 평가 이력만 안다.

## 데이터 경계

| 데이터 | 역할 |
| --- | --- |
| `AccountingBook` | 소유자 ID, 선택적인 개인·사업 구분(`scope`), 장부 종류, 단위. 다른 장부·소유자·단위의 잔액은 합산하지 않는다. |
| `AccountingUnit` | ID, 이름, 기호, 차원(`currency` / `time` / `quantity`), 소수 자릿수(`scale`). |
| `AccountingAccount` | 안정적인 ID, 장부 ID, 이름, 유형, 선택적인 상위 계정 ID. 이름으로 로직을 선택하지 않는다. |
| `AccountingEntry` | 활동 ID, 장부 ID, 발생·기록 시각, 출처, 원본 기록 ID, 복수 분개 항목, 원본/평가 구분. |
| `AccountingPosting` | 계정 ID, 차변/대변, 양의 정수 최소단위 수량. |
| `AccountingAssessment` | 원본 분개 ID, 판단 근거, 신뢰도, 평가 모델/평가자, 선택적인 이전 평가 ID. |

계정 유형은 `asset`, `liability`, `equity`, `income`, `expense`다. 새 생활 사례는 이 열거형을 확장하지 않는다. 예를 들어 교육비·외국어 교육비·직무 교육비는 비용 계정 데이터이며, 관리용 역량은 자산 계정 데이터다. 계정 ID는 표시 이름과 분리한다. 상위 계정은 같은 장부·유형이어야 하며 순환을 허용하지 않는다.

금액은 `Int` 최소단위로 기록한다. `scale=0`의 KRW 100000은 100,000원, `scale=2`의 123은 1.23단위다. 예시 시간 장부는 분 단위여서 2시간을 120으로 저장한다. `Double`로 금액을 더하거나 원과 분을 합산하지 않는다. 비율은 1/10000 단위(`basisPoints`), 신뢰도는 별도 값이다. 비율 계산은 최소단위 반올림을 사용한다.

`financial` 장부에는 화폐 단위만 허용한다. 시간과 다른 수량은 `resource` 장부로 기록한다. 시간예산 배정, 사용, 소멸도 같은 차변·대변을 사용한다. 원장은 기록의 차대 일치를 검증하며, 시간을 자동 배정하거나 미래의 시간을 실제 보유 자산으로 만들지 않는다.

원본 금융 거래, 잔액 관측, 체중 측정, 증빙은 수집 자료다. 흐름이 확인된 자료를 공통 분개로 연결한다. 체중 스냅샷 하나를 체중 증가 거래로 바꾸는 식으로 존재하지 않는 움직임을 생성하지 않는다. 기존 건강/OCR 코드는 출처를 읽고 검증하는 어댑터로 유지한다. 자기개발을 추가하기 위해 `LifeRecord.Kind.study` 같은 전용 타입은 만들지 않는다.

## 개인·사업·소유자 경계

장부의 `scope`는 공통 `RecordScope`를 사용한다. 계정 이름이나 활동 이름에서 개인·사업 여부를 추측하지 않는다. 개인 활동과 사업 활동은 같은 엔진과 화면을 사용하며, 같은 소유자에게 사업이 여러 개 있으면 사업별로 별도 장부를 정의한다. 한 사업에서 돈과 시간을 기록하는 경우에도 단위마다 장부를 분리한다.

| `scope.kind` | 의미와 필수 참조 |
| --- | --- |
| `unclassified` | 개인·사업 귀속 미분류. 소유자 ID는 선택 사항이며 사업 ID를 넣지 않는다. |
| `personal` | 개인 자료. `ownerID`가 필요하며 `businessID`를 넣지 않는다. |
| `business` | 사업 자료. `ownerID`와 `businessID`가 모두 필요하다. |

`AccountingBook.ownerID`는 계속 필수다. 명시한 `scope.ownerID`는 장부의 소유자 ID와 같아야 한다. 한 회계 저장소에서 같은 `businessID`를 서로 다른 소유자에게 연결할 수 없다. 같은 소유자가 같은 사업 ID로 여러 장부를 정의하는 것은 가능하다. `ownerID`와 `businessID`는 안정적인 불투명 참조 ID이며 표시 이름이나 사업자등록번호로 대체하지 않는다.

계정의 상위 계정, 분개 항목, 평가 원본과 교체 이력은 같은 장부 안에서만 참조한다. 같은 소유자·화폐·활동 ID를 사용해도 서로 다른 사업의 계정으로 분개하거나 재분류할 수 없다. 사업 간 거래가 실제로 발생했다면 확인된 출처에 따라 각 장부에 별도의 균형 분개를 기록하고 공통 활동 ID로 연결한다. 사업 구분 자체는 회계 이동을 생성하지 않는다.

이전 JSON에 `scope`가 없으면 그대로 읽고 저장한다. 표시·필터용 `effectiveScope`만 `unclassified`와 기존 장부의 `ownerID`로 계산하며 개인 장부라고 추정하지 않는다. 조회·내보내기·재시도는 원본 `scope` 누락과 기존 분개·평가 이력을 보존한다. 기존 장부 ID에 나중에 다른 `scope`를 붙이는 가져오기도 내용 변경으로 거절한다.

새 구분의 엄격한 ID 형식은 명시적으로 저장한 `scope`에만 적용한다. 이전 장부에서 허용하던 소유자 참조 문자열은 앞뒤 공백·제어문자가 있더라도 원문과 기존 검증 규칙을 유지하며, 표시용 미분류 구분 때문에 과거 저장소 전체를 읽지 못하게 만들지 않는다.

## 왼쪽 원본과 오른쪽 평가

`layer=recorded`에는 실제 보고·관측을 바탕으로 기록한 원본 분개를 저장한다. 기록된 분개라는 뜻이며 감사·사용자 검토 완료를 보증하지 않는다. 소비 지출은 비용으로 기록하고, 이체·대출 상환·자산 취득 같은 원래의 회계 구분은 유지한다.

`layer=adjustment`는 원본을 참조하는 별도 관리용 평가다. 오른쪽 장부는 원본과 현재 유효한 평가 조정을 계정별로 합쳐 보여준다. 예를 들어 원본 `교육비 차변 100000 / 예금 대변 100000`에 `역량 차변 60000 / 교육비 대변 60000`을 더하면 오른쪽은 `역량 60000 + 교육비 40000 / 예금 100000`이다. 예금이 두 번 줄지 않는다. 이 60%는 설명용 가정이며 앱의 기본값이 아니다.

시간도 같은 엔진으로 `학습사용 차변 120 / 가용시간 대변 120`에 `미상각투입 차변 72 / 학습사용 대변 72`를 적용할 수 있다. 72분은 미래 효용이 남았다고 추정하는 과거 투입량이다. 앞으로 사용할 수 있는 시간이나 역량의 시장가격을 뜻하지 않는다. 원화 환산이나 실제 금융 순자산과의 합산은 수행하지 않는다.

원본당 평가 체인은 하나다. 여러 계정에 배분하려면 한 평가에 여러 분개 항목을 넣는다. 수정은 새 ID와 `replacesEntryID`로 이전 평가 전체를 대체한다. 기존 판단은 남지만 현재 보고서에는 최신 판단만 들어간다. 동일 평가를 동시에 두 번 대체하면 충돌로 거절한다. 자산화 비율을 0%로 수정할 때는 이전 평가를 대체하는 빈 조정을 남겨, 이력과 이유를 보존하면서 원본으로 돌아간다.

분개는 자산화·상각·손상·환불·시간 사용에 공통이다. 현재 구현은 자동 상각 스케줄러나 AI 효율 예측 모델을 포함하지 않는다. 외부 AI/사용자가 근거 있는 평가를 제출하면 공통 API가 검증·저장·표시한다. 정식 재무 장부에 개인 역량의 가상 가치를 자동 반영하지 않는다.

## 앱과 API

기록 영역의 **분개장**에서 개인·사업·미분류 및 소유자·사업 ID로 범위를 좁히고 장부를 선택하면 왼쪽 원본과 오른쪽 관리 장부가 나온다. 전체 장부가 없는 상태와 선택한 범위에 장부가 없는 상태를 구분한다. 계정 이름·계층·단위는 저장된 정의를 사용한다. 오른쪽에는 판단 근거, 신뢰도, 모델/평가자, 평가 시각, 교체한 평가와 실제 조정 분개를 표시한다. 새로고침으로 대화에서 저장한 최신 기록을 읽을 수 있다.

**가져오기·내보내기**에서 장부 JSON, 기존 수집 장부, 전체 백업, 가상 예시를 다룬다. 예시는 자동 저장하지 않는다. 가상 자료와 실제 자료의 소유자 ID를 혼용하지 않는다.

음성과 MCP는 동일한 도구를 제공한다.

| 도구 | 동작 |
| --- | --- |
| `accounting_template` | 계정 정의와 가상 분개를 포함한 JSON 예시 조회. 저장하지 않는다. |
| `accounting_records` | `scopeKind`·`ownerID`·`businessID`·`bookID` 범위의 장부·계정·분개 조회. `entryID`는 오래된 원본/평가를 직접 조회하며 `eventID`는 같은 활동의 여러 단위를 연결한다. `history=true`는 이전 평가도 반환한다. 기본 100건, 최대 1000건, `nextOffset`으로 다음 페이지 조회. |
| `accounting_import` | 계정·장부·분개 JSON을 원자적으로 추가. 이미 등록된 정의는 생략 가능. |
| `accounting_reclassify` | 원본의 특정 항목을 지정 비율로 다른 계정에 재분류. 동일 함수로 금액·시간·수량을 처리. |

`accounting_import.archive`는 `{ "formatVersion": 1, "books": [], "accounts": [], "entries": [] }` 형식의 JSON 문자열이다. 발생·기록 시각은 시간대를 포함한 ISO8601이다. 전체 예시는 [번들 예시](../Ppomi/Sources/Ppomi/AccountingData/example.json)를 참조한다.

범위 필터는 모두 AND 조건이다. `businessID`만 지정하면 해당 사업 자료를 선택하며 `scopeKind=personal` 또는 `unclassified`와 함께 지정하면 오류다. `bookID`가 범위 필터와 충돌해도 명시적으로 오류를 반환한다. 존재하지 않는 범위는 빈 결과를 반환한다. 필터는 응답의 `data.books`, `data.accounts`, `data.entries`에 함께 적용하며 `entryID`, `eventID`, `history=true`로 다른 범위의 자료를 가져올 수 없다.

응답의 `scopeByBookID`는 선택된 장부 ID를 표시·필터용 `effectiveScope`에 연결한다. `data.books`에는 저장된 원본 정의를 그대로 반환하므로 이전 자료의 `scope`를 새 값으로 채워 넣지 않는다. 다음은 같은 소유자의 사업 하나에서 평가 이력까지 조회하는 요청이다.

```json
{
  "scopeKind": "business",
  "ownerID": "owner-example",
  "businessID": "business-example",
  "history": true
}
```

새 사업은 `scope={"kind":"business","ownerID":"owner-example","businessID":"business-example"}`인 장부와 해당 장부의 계정 데이터로 추가한다. 번들 가상 예시는 개인 금전·시간 장부와 같은 소유자의 별도 사업 장부를 포함한다. 사업 예시는 빈 장부이며 사업이나 계정이 존재한다는 이유로 거래·수익을 만들어 넣지 않는다.

재분류 호출 예시(해당 원본과 계정이 등록되어 있어야 함):

```json
{
  "id": "assessment-001",
  "sourceEntryID": "entry-001",
  "postingIndex": 0,
  "targetAccountID": "account-capability",
  "basisPoints": 6000,
  "rationale": "사용자가 제출한 결과물을 토대로 정한 관리상 배분 가정",
  "confidenceBasisPoints": 4500,
  "model": "평가자 또는 실제 사용 모델"
}
```

같은 요청의 재시도에는 같은 ID를 사용한다. 수정은 새 ID와 `replacesEntryID`를 사용한다. 가져오기는 이미 저장된 ID의 내용 변경을 거절한다. 같은 장부·출처·원본 기록 ID를 다른 분개 ID로 중복 저장하는 것도 거절한다. 원본 사실 정정은 기존 원본의 덮어쓰기 대신 출처를 명시한 역분개와 새 분개로 기록한다.

## 저장과 이전 자료

비공개 저장소는 `~/Library/Application Support/Ppomi/Private/accounting.sqlite`다. 디렉터리 권한은 0700, DB·내보내기 파일 권한은 0600이다. 장부·계정·분개를 JSON payload로 보존하며 전체 가져오기를 SQLite 트랜잭션으로 묶는다. 같은 파일을 쓰는 앱·MCP 연결은 기존 DB의 파일 단위 잠금과 SQLite 쓰기 트랜잭션을 사용한다. 충돌·검증 실패는 전부 롤백한다. 실제 사용자 장부에 테스트·예시를 삽입하지 않는다.

기존 장부 가져오기는 명시적 버튼으로 실행한다. 메모에서 추정한 추가 현금 지출은 원본에서 제외하고, 확인된 거래의 비용·환불·이체·수입을 옮긴다. 잔액 스냅샷으로 기초 잔액을 임의 생성하지 않으므로 거래만 가져온 장부를 완전한 재무상태표로 해석하지 않는다.

기존 원장의 이름 기반 계좌 식별은 한계가 있다. 원본 DB의 정규화 경로 해시를 namespace로 사용해 다른 DB와 분리하며 원본 경로는 내보내지 않는다. 같은 파일을 다른 경로로 옮겨 다시 가져오면 별도 원본으로 간주하므로 이전 장부와의 중복 여부를 확인해야 한다. 소유권은 추정하지 않고 장부 이름에 ‘소유 미확인’을 표시한다. 원본에 실제 수집 시각이 없는 레거시 분개는 발생 시각을 기록 시각에도 보존한다.

기존 가맹점·은행·카테고리 분류 정책은 [legacy-rules.json](../Ppomi/Sources/Ppomi/AccountingData/legacy-rules.json)의 데이터다. Swift 호환 어댑터는 이 데이터를 읽어 이전 타임라인의 동작을 유지한다. 새로운 정식 분개는 이 레거시 이름 기반 모델에 사례를 추가하지 않고 공통 계정 ID와 postings를 직접 사용한다.

## 변경 원칙

1. 새 생활 사례에는 계정 데이터·계층·활동 ID를 추가한다.
2. 새 입력 기기/서비스가 필요할 때만 출처 어댑터를 추가한다.
3. 계산·잔액·분개·비교 화면에 특정 가맹점, 학습 종류, 건강 활동 이름으로 분기하지 않는다.
4. 엔진 코드는 개인·사업·소유자 구분의 일관성, 계정 참조·장부 경계·단위·정밀도·차대 일치·평가 이력을 검증한다.
