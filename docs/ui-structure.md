# 작업대 UI 구조

## 기록 집중 규칙 (Mac·Android 공통)

기록은 요약 띠가 아니라 **기록 페이지**다(docs/ui-tree.md): 제어 머리띠의 "기록"이 작업 공간(대화·제어)을 통째로 페이지로 바꾸고, 페이지 머리띠는 "← 대화" + 탭이다. 페이지로 갈 때 대상 창을 숨긴다: 제어창 최소화를 먼저 시도하고, 거부되면(스테이지 매니저·iPhone 미러링) 도킹을 풀어 작업대를 불투명하게 만들고 뽀미를 활성화해 앞으로 올려 덮는다. "← 대화"(Esc)로 도킹이 돌아온다. 질문(승인)이 오면 페이지를 떠나며, 질문 중·뽀미 진행 중에는 "기록"이 비활성이다. Android는 대화 화면을 떠나 작업·기록·설정·공유 화면으로 가면 제어 자리를 접고 대상 팝업을 캡션(손잡이 탭 → 최소화)으로 최소화하며, 대화로 돌아오면 최소화 아이콘을 눌러 복원한다(`BridgeAccessibilityService.setControlWindowHidden`). 2026-09-10 Mac에서 집중 진입 시 작업대가 미러링 창 위로 올라와 가리고, 복귀 시 자리에 다시 붙는 것을 캡처로 확인했다. Android는 같은 날 Galaxy Fold에서 최소화·전체 폭·복원까지 확인했다(docs/android-control.md).

## 색·글꼴·크기 규칙 (Mac·Android·웹 공통)

색은 둘뿐이다: `agent/theme.json`의 primary(잉크 #111, 글자이자 다크 바탕)와 accent(파랑 #3b82f6, 아껴 쓰는 강조 하나). 기준은 agentation.com의 절제 — 흰 면, 잉크 글자, 몇 % 헤어라인, 강조색은 주 동작 하나와 선택 상태에만. 배합표는 `agent/scripts/generate-theme.mjs` 한 곳뿐이며, 라이트·다크 두 세트(배경·면·선·글자·강조 파생·on-accent·bad)를 계산해 `agent/src/generated/theme-colors.css`, `Ppomi/Sources/Ppomi/Views/Palette.generated.swift`, `Android/.../ThemeColors.kt`, `res/values/theme_colors.xml`로 쓴다. 어느 플랫폼도 색을 직접 섞지 않고 생성된 값만 읽는다(웹 `tokens.css`는 글꼴·단·배율만, Mac `Palette.swift`와 Android `Theme.kt`는 생성값을 NSColor·Color로 감쌀 뿐). on-accent는 accent 밝기로 흰색/잉크를 고른다. 라이트·다크는 시스템을 따르고 어느 플랫폼도 어둡게 고정하지 않는다. 상태색은 차례(사람)=글자색 테두리 하나뿐이다.

글꼴은 세 곳 모두 번들한 Pretendard Variable이고(웹 `agent/public/fonts`, Mac `Fonts/`, Android `res/font`; 라틴은 Inter 그대로라 agentation과 같은 인상), 글자 크기는 11·12·14·16·21·24 여섯 단만 쓴다. 굵기는 400(본문)과 500(제목·동작·금액·선택 탭) 둘뿐이고 600 이상은 없다. 자간은 21·24 두 단에만 −0.01em, 숫자 열(금액·건수·날짜)은 tabular figures다(웹 `.num`, Mac `monospacedDigits: true`, Android `tnum`). 폰트가 실제로 로드되는지는 Mac `WebFontTests`(파일 URL로 연 페이지에서 `document.fonts.check`)와 APK·dist의 폰트 파일 존재로 확인한다. 전체 배율은 하나의 값이다: 웹은 `html{font-size: 16px × --ui-scale}`에 rem, Mac은 설정의 "글자 크기"(`AppSettings.uiScale`), Android는 시스템 글꼴 배율(`fontScale`). 부트스트랩의 `uiScale`로 네이티브가 웹에 넘기며, 글자만이 아니라 여백·컨트롤도 같이 커진다. Android의 WebView는 액티비티보다 오래 살아 시스템 테마를 스스로 따라가지 못하므로, 붙일 때마다 호스트가 `data-theme`와 `--ui-scale`을 페이지에 직접 넣는다(`VoiceSessionHost.applyAppearance`). Mac은 레이아웃 높이(툴바·차례 띠)와 시스템 컨트롤 크기도 같은 배율을 따른다(`WorkbenchLayout.scale`, `ControlSize.ppomi`). 2026-09-10 Mac(라이트 2×·다크 1×)과 Galaxy Fold(다크 1×·라이트 2×)에서 같은 모습을 캡처로 확인했다. 말은 최소한으로: 라벨은 한두 단어, 안내는 명사구 하나.

## 제어 자리 규칙 (Mac·Android 공통)

뽀미 UI는 제어 대상 창을 위한 빈 사각형, 곧 **제어 자리**를 둔다. 제어 열 폭 = 대상 창 폭 + 간격 2(없거나 작으면 작은 iPhone 폭 232 + 간격), 대화 열이 나머지를 가진다(`WorkbenchLayout.dashboard`). 제어 머리띠는 대상 선택기와 "기록"뿐이다. 창이 자리보다 크면 안내 한 줄만 둔다. Mac에서는 iPhone 미러링·Android 미러·Parallels 창이고, Android에서는 대상 앱의 팝업(자유) 창이다. 두 앱은 같은 규칙을 따른다.

1. 대상 창이 없으면 자리에는 한 줄뿐이다: 대상 이름 · 연결 끊김, 또는 안내(Mac `DockView`, Android `ControlSlotColumn`).
2. 대상 창이 있으면 자리는 그 창의 실제 좌표를 따라가고 뽀미 콘텐츠는 그 사각형을 비켜 간다(Mac `followedPhone`, Android `rememberControlSlot`). 크기는 대상 앱과 시스템이 정하며 뽀미는 명시적 배치 동작에서만 한 번 옮긴다.
3. 자리 테두리는 사람 차례(승인·질문)일 때만 잉크 2pt다. 그 외에는 테두리가 없다(진행은 구멍 속 화면이 보여 준다).
4. 자리를 둘 폭이 없는 좁은 화면(Android 720dp 미만)에서는 자리를 두지 않고 대상 앱 위의 하단 패널로 대신한다. 대상 창이 전체 화면이나 분할로 뽀미 창을 덮으면 비울 것이 없으므로 자리를 두지 않는다.
5. Android에서 대상 창을 팝업으로 만드는 경로는 런처의 최근 앱 메뉴(`BridgeAccessibilityService.openAsPopup`)다. 앱이 직접 분할·팝업을 만드는 API는 없고, 삼성 기기에서 접근성 전역 동작의 분할 토글은 거부된다(2026-09-10 Galaxy Fold 확인).

2026-09-10부터 Mac의 일반 실행과 Dock 재열기는 작업대를 열고 그 왼쪽 대화 열에 뽀미 자체 대화를 넣는다(`AgentSidebar: ConversationHost`). 오른쪽은 제어 자리다. 에이전트 열은 직접 구축한 뽀미 에이전트만 둔다. ChatGPT·Codex 외부 대화창 배치(`AgentDockCoordinator`·`AgentWindow`·`AgentDockLayout`)는 같은 날 제거했다. 작업대 창을 닫으면 대화 세션과 마이크도 끝나고, ⌥Space·호출어·도착 인사는 `AppState.showWorkbench()`로 창을 다시 띄운다. 키오스크의 대화 덮개는 활성화 없이 키 창이 되어 채팅 입력을 받는다. Android와 같은 번들 React 대화 껍데기를 신뢰된 로컬 WebView에 표시한다.

작업대 창은 2026-09-10부터 이동·크기 조절이 된다. 최소 크기는 `WorkbenchLayout.minimumContentSize`(1040×640pt: 작은 iPhone 미러 232×515와 머리띠를 담는 높이)이고, 처음 실행에서만 디스플레이 가용 영역에 맞추며 이후에는 사람이 정한 프레임을 기억(`workbench` 자동 저장)한다. 디스플레이가 바뀌면 프레임을 줄이지 않고 디스플레이 안으로 옮기고, 디스플레이가 최소보다 작으면 디스플레이 크기를 따른다(`KioskController.fitted`). 창을 옮기면 도킹 틱이 제어창을 새 자리로 맞추고, 크기 조절 중(`inLiveResize`)에는 외부 창을 건드리지 않는다.

작업대 창은 2026-09-10부터 보통 창이다. 클릭하면 뽀미가 활성화되고, 스테이지 매니저에서는 자기 스테이지를 가지며 다른 앱으로 가면 왼쪽 띠로 내려간다(예전의 "모든 앱 스테이지에 깔리는 활성화 없는 동반 패널"은 폐기). 제어창은 같은 스테이지에 있을 때만 자리에 붙인다. 다른 스테이지의 창은 띠의 썸네일(높이 200pt 미만)이라 살아 있는 창이 아니며, 자리에는 "다른 스테이지에 있음" 한 줄만 둔다. 서로 다른 앱의 창을 한 스테이지로 묶는 API는 없으므로, 뽀미가 앞에 있고 포인터가 쉬고 있을 때 도킹 틱이 사람의 동작을 대신한다. 띠의 썸네일을 잡아 제어 자리로 끌어다 놓는 합성 드래그(`StageDrag`, `dock.stagePull`)를 썸네일 상태마다 한 번 실행하고 커서를 제자리로 되돌린다. 그 뒤로는 스테이지 매니저가 묶음을 기억해 함께 내려가고 함께 돌아온다. 2026-09-10 확인: 미러링이 별도 스테이지인 상태에서 뽀미를 실행하자 3초 안에 스스로 썸네일을 끌어와 자리에 붙였고, Claude로 갔다가 Dock으로 돌아와도 묶음이 유지됐다.

창 순서로 짝을 맞추던 방식(작업대를 항상 제어창 바로 아래로 정렬)은 폐기했다. 대신 제어 자리와 외부 대화창 자리는 작업대 창에 뚫린 **투명 구멍**이라(`WorkbenchContent.dockedPhone`, 창 배경 clear), 도킹된 네이티브 창은 작업대 위에 있든 아래에 있든 그 자리에 보인다. 다른 앱 창이 둘 사이에 끼어 구멍에 그 앱이 비치면 제어창만 끌어올린다(`dock.raiseReveal`). 포인터가 구멍 위에 있는 동안 작업대 창은 마우스 이벤트를 무시해(`ignoresMouseEvents`, 도킹 틱마다 갱신) 클릭이 구멍 속 네이티브 창으로 간다.

대화 열기(메뉴·Dock)와 일반 활성화(⌘Tab·클릭)에서는 손쉬운 사용 권한이 있고 제어창이 살아 있지만 다른 앱에 묻혀 있을 때만 제어창을 앞으로 올린 뒤 뽀미를 다시 활성화한다. 다른 스테이지의 썸네일은 위의 합성 드래그가 맡는다. 활성화 전환 중의 AX 요청은 무시되므로 전환이 끝난 뒤(0.15초)에 실행한다. 제어 앱으로 넘어간 활성화는 되찾지 않으며 패널은 활성화 없이 키 창이 된다. 권한이 없으면 짝을 맺지 않고 작업대만 앞에 둔다. 다른 앱 창이 작업대와 제어창 사이에 끼면 도킹 틱이 제어창을 올리고 앱을 활성화한다(`dock.raiseReveal`, 2초에 한 번). 활성화 관찰자는 작업대가 키 창일 때만 동작해 설정 창 같은 다른 뽀미 창의 키 상태를 빼앗지 않는다. 채팅과 음성은 같은 헤더·탭·도구 내역·질문 카드·입력 자리를 쓰며, 음성은 말풍선 자리에 상태를 둔다. 입력창이 창 안에 유지되도록 높이를 채운다. 질문 카드는 두 플랫폼 공통이고, 은행정보 카드는 기기에서 은행 프로필을 지원할 때만 연다. 음성 호출 설정을 끄는 동작과 현재 대화 종료는 분리한다.

아래 작업대 구조는 메뉴의 기록·기기 제어와 명시적 키오스크 진입에서 계속 사용한다. `state.reveal()`의 제어·기록 의미를 유지하고, 일반 대화 진입은 별도 `openChat()`으로 전달한다. Mac의 안내 예시는 실제 제공되는 플레이북 조회이며 Android 앱 제어 기능을 Mac에도 제공한다고 표시하지 않는다.


2026-09-10 구현 기준. 작업 공간은 왼쪽 대화(셸만, 머리띠·푸터 없음)와 오른쪽 제어(머리띠 + 자리)다. 상시 기록 띠는 없다. 두 열은 제어창의 위치에 따라 서로 바뀌지 않는다.

차례 띠(`PhoneBand`: 질문 한 줄 + 버튼)는 제어 열 아래에 사람 차례일 때만 있고, 없을 때는 높이 0이다(`WorkbenchLayout.pane`). 대화 열 아래 상태 푸터는 없다(셸이 자기 상태를 보인다). 기록 페이지의 탭은 segmented 형식이다.

## 네이티브 뷰 소유

| 소유자 | 책임 |
|---|---|
| `WorkbenchContent` | 대화 영역, 제어 머리띠, 제어 자리, 차례 띠, 기록 페이지의 직접 자식을 배치한다. |
| `WorkbenchLayout` | 두 열(대화=나머지, 제어=대상 창 폭)과 제어 열의 머리띠·자리·차례 띠를 순수 기하로 계산한다. |
| `WorkbenchContentHost` | 빌려준 콘텐츠를 유지하고 일반 창으로 회수한다. 현재 직접 자식인 콘텐츠만 배치한다. |
| [`RecordsView` / `RecordsPageHost`](../Ppomi/Sources/Ppomi/Views/RecordsView.swift) | 기록 탐색과 각 페이지를 소유한다. 페이지는 처음 선택할 때 생성하고 탭별 호스트를 캐시한다. |
| `AgentSidebar` / `PhoneBand` | 자체 대화 뷰의 자리(`ConversationHost`)와 차례 띠(사람 차례일 때만)를 각각 소유한다. |
| `AgentVoicePanel` | 신뢰된 번들 대화 문서를 자체 창 또는 작업대의 `ConversationHost`에 띄운다. 어느 쪽이든 닫으면 세션을 끝낸다. |
| `ImmersiveKiosk` | 같은 대화·머리띠·자리·차례 띠·기록 페이지를 영역별 덮개에 빌려 배치한다. 별도 페이지 상태를 만들지 않는다. |

레이아웃 코드는 직접 자식의 프레임만 변경한다. 키오스크에 빌려준 뷰는 일반 창이 계속 배치하지 않으며, 현재 `superview`가 맞는지 확인한다. 일반 창·키오스크가 같은 `WorkbenchLayout` 계산을 사용해 영역의 의미를 공유한다.

iPhone 미러링·Android 미러·Parallels 창은 다른 프로세스의 네이티브 창이다. 작업대의 `NSView` 자식이나 복제된 화면으로 취급하지 않는다. 외부 창 조정은 `WorkSurface`의 경계에서 수행하고, 앱 식별·창 선택·실제 프레임 확인을 거친다.

## 상태와 페이지 수명

`AppState`는 기록 페이지 여부, 기록 탭, 제어 대상처럼 작업대 전체에 필요한 상태를 소유한다. 건강 기록의 대상·기간·선택, 절차의 선택 앱은 해당 페이지가 소유한다. 기록 페이지 진입과 탭 이동은 캐시된 호스트의 표시만 바꾸어 이 상태와 실제 WKWebView를 유지한다. 숨기는 페이지에 입력 포커스가 남아 있으면 해제한다.

`recordsPageIsActive`는 전체 기록이 펼쳐져 있고 해당 탭이 선택된 경우에만 참이다. 건강·절차 페이지의 주기적 조회는 이 값에 연결한 취소 가능한 작업으로 실행한다. 캐시된 비활성 페이지는 상태를 유지하지만 저장소를 주기적으로 읽지 않는다.

`HealthModel`과 `PlaybooksModel`은 파일·DB 조회 결과를 비동기 스냅샷으로 받아 UI 상태를 갱신한다. 오래된 요청의 완료가 더 최근 결과를 덮지 않도록 요청 세대를 확인한다. 절차 아이콘의 파일 읽기는 뷰 렌더링에서 수행하지 않고, 변경된 이미지 데이터를 캐시에 반영한다. 건강 화면은 측정·요약·기록 목록으로 분리하며, 목록은 지연 렌더링과 ‘더 보기’로 오래된 기록까지 접근하게 한다.

## 도구 호출 상태

호출 상태를 항상 그리는 뷰는 없다(`ToolActivityPresentation`은 해석만). 사용자 응답을 기다리는 질문은 차례 띠에 표시한다.

| 계층 | 책임 |
|---|---|
| `MCPServer` / `Tools` / `Replay` | 호출 시작·반환과 실제 OCR, VLM 요청·응답, 제어, 예상 화면 검증, 사람에게 넘김을 관측한다. |
| `RuntimeRecorder` | 같은 동기 호출의 중첩 래퍼를 하나의 호출 ID로 묶고 고정 어휘의 이벤트를 기록한다. 기록 오류는 원래 도구 반환값을 바꾸지 않는다. |
| `RuntimeEventStore` | 장부 경로별 별도 `.runtime.sqlite`에 최근 500개 이벤트를 삽입 순서로 보존한다. |
| `RuntimeEventMonitor` / `RuntimeActivity` | 백그라운드 읽기 전용 연결로 커밋을 감시하고, 경로 전환·중지 때 이전 결과를 차단한다. |
| `ToolActivityPresentation` | 호출별 상태를 해석한다. 파일이나 DB를 읽지 않는다. |

`RuntimeActivity`는 `AppState`와 별도 관찰 객체다. 약 0.4초 간격의 상태 수집이 장부를 다시 읽거나 작업대 전체를 갱신하지 않도록 분리한다. 파일 오류가 나면 마지막 정상 이력을 유지하면서 수집 불가를 표시한다. 종료 이벤트 없이 30초 동안 갱신되지 않은 호출은 ‘상태 미확인’이며, 자동으로 실패나 완료로 바꾸지 않는다.

OCR → VLM → 에이전트는 강제 실행 순서가 아니다. VLM은 요청된 경우에만 관측하고, 외부 에이전트의 내부 실행은 추정하지 않는다. 재생이 확인하는 것은 저장된 예상 화면과의 일치이며, 알려진 경로의 끝은 에이전트에 반환으로 표시한다. 도구 응답 반환 역시 업무 완료를 의미하지 않는다. 선택적 발자국 기록을 위한 추가 화면 읽기 실패는 주동작 실패와 구분한다.

이벤트에는 허용 목록의 도구 이름, 고정 상태·방법, 시각, 임의 호출 ID, 재생 동작 번호만 넣는다. 도구 인수·응답 본문·화면·OCR 원문·입력값·프로필은 이 저장소에 넣지 않는다. 실행 중이던 이전 버전의 MCP 프로세스는 재연결되기 전까지 새 이벤트를 만들지 않는다.

## 외부 창 크기

명시적인 다시 배치, 제어 대상 변경, 기록 페이지 복귀, 창 모드·디스플레이 변경은 한 번의 크기 요청을 허용한다. 후속 타이머는 요청 완료와 실제 프레임을 확인하며 반복 축소를 수행하지 않는다. 외부 앱이 허용하는 최소 크기를 우선하고, 기록·도구막대·승인을 침범하는 프레임은 사용하지 않는다.

- iPhone은 미러링 앱의 **보기 → 작게 / View → Smaller** 메뉴가 활성화된 경우에만 실행한다. 임의 AX 크기를 강제로 쓰지 않는다. 점검 당시에는 iPhone을 사용할 수 없어 메뉴가 비활성이었으므로 연결 후 실제 크기 변경은 미확인이다.
- Windows는 현재 네이티브 창을 비율 보존으로 축소하며 이미 작은 창을 확대하지 않는다. 축소 후에는 같은 AX 창을 유지해 더 큰 설정 창으로 대상을 바꾸지 않는다. Parallels PiP로 강제 전환하지 않는다.

## 웹 DOM 원칙

타임라인과 증빙 페이지는 `main`, `section`, 제목, 탐색 영역으로 구조를 드러낸다. 상위 화면은 섹션별 렌더러를 조합하고, 거래·앱 탐색은 실제 버튼과 부모 이벤트 처리로 연결한다. 데이터 문자열은 HTML 텍스트·속성에 맞게 이스케이프한다.

Swift와 웹의 경계는 `WebPage`가 소유한다. 자바스크립트 인수는 JSON으로 직렬화하고 웹 메시지는 메인 프레임에서만 받는다. 같은 HTML에 대한 일반 앱 상태 변경이나 탭 왕복은 페이지 전체를 다시 로드하지 않는다. 타임라인은 장부가 바뀌어도 기존 문서에 데이터만 전달해 날짜·기간·스크롤을 유지한다. 증빙은 새 HTML을 로드한 뒤 선택 UID의 포커스를 다시 적용한다.

`LedgerMonitor`는 읽기 전용 연결에서 커밋된 장부 변경을 약 1초 간격으로 확인한다. 실제 장부 내용이 바뀐 경우에만 UI를 갱신하며, 실패한 읽기로 기존 값을 지우지 않는다. 설정의 경로·이름은 임시 입력으로 유지하고, ‘장부 설정 적용’에서 검증한 뒤 장부·승인 연결을 함께 바꾼다.

같은 DB를 여는 앱 내부 연결은 정규화하고 심볼릭 링크를 해석한 경로별 잠금을 공유한다. 장부·건강 기록의 읽기 트랜잭션과 설정 검증은 시작부터 종료까지 이 잠금을 유지한다. 2026-09-08 이 Mac의 시스템 SQLite 3.51.0에서 동일 프로세스의 읽기 전용 연결과 쓰기 연결이 경합하면 `SQLITE_IOERR_LOCK / EBADF`가 발생하는 현상을 독립 C·Swift 재현으로 확인했다. 경로별 직렬화로 읽기 전용·기존 저널 정책을 유지하며, 외부 프로세스의 짧은 읽기와 경합하는 쓰기는 최대 1초 기다린다.

## 검증 범위

자동 검증은 다음 성질을 대상으로 한다. 통합 빌드·테스트의 실행 결과와 실제 앱 검증 결과는 별도로 기록한다.

- 두 열이 겹치지 않고, 제어창 이동이 다른 영역의 위치를 바꾸지 않는지.
- 양쪽 헤더·본문의 시작 높이·푸터가 같은 기하를 사용하고, 네이티브 창이 커도 기록의 최소 높이를 침범하지 않는지.
- 키오스크로 빌려준 뷰를 이전 부모가 배치하지 않으며 복귀 시 같은 뷰가 회수되는지.
- 탭별 기록 페이지가 지연 생성되고, 탭 왕복 뒤 실제 DOM 노드·기간·선택일·입력·스크롤이 유지되는지.
- 저장된 장부가 변경되어도 타임라인의 기간·선택일·스크롤·문서 노드를 유지하며 값만 갱신하는지.
- 특수 문자가 포함된 장부 데이터·UID가 마크업이나 실행 코드로 해석되지 않는지.
- Windows 축소가 비율·영역·최소 크기를 지키고 축소 뒤 창 식별을 유지하는지.
- 실제 별도 MCP 프로세스의 호출이 하나의 이력으로 도착하고, 여러 호출이 섞이지 않으며 장부 변경 버전을 건드리지 않는지.
- 호출의 실패·차단·외부 인계·오래된 상태를 구분하고, 원문이 실행 이력에 남지 않는지.

실제 iPhone의 ‘작게’ 실행, Parallels가 요청 크기를 수용하는 범위, 외부 앱 최소 크기, 접근성 권한, Stage Manager/Spaces 순서, 화면 전환과 키오스크 복귀는 실제 Mac에서 확인해야 한다. 실행 결과는 확인 시점과 조건을 함께 기록한다.

2026-09-08 최종 검증: Swift 테스트 269개 중 268개 통과, 유료 API 실기 1개 건너뜀, 실패 0. 동일 개발 서명으로 `/Applications/뽀미.app`을 교체·실행하고 제목·탭·푸터의 좌우 정렬과 `ChatGPT / Codex`, `iPhone / Windows` 레이블을 실제 앱에서 확인했다. 관측된 작업대 1728×1084, 대화창 840×752, Windows 824×754 크기를 회귀 사례로 추가했다. 공통 세로 간격 8pt에서 요약 상태의 양쪽 본문 영역은 840×764이며, 네이티브 창의 시작 높이와 푸터 위치를 함께 검증한다. 별도 입력 작업에서 Windows를 다시 확대한 상태의 최종 네이티브 재배치는 그 작업과 겹치지 않도록 남겨 두었다.

같은 날 도구 호출 상태 추가 후 통합 검증: 332개 중 331개 통과, 유료 API 실기 1개 건너뜀, 실패 0. 별도 MCP 프로세스의 시작·결과 반환, 중첩 호출 ID, OCR/VLM 캐시·재생 이력, 부가 기록 실패, 동시 저장·감시·경로 변경, 시각 정밀도 보존을 검증했다. 개발 서명 릴리즈에서도 읽기 전용 `SELECT 1` 호출이 별도 실행 저장소에 한 호출로 도착했다. 새 릴리즈의 실제 요약·상세 화면 검증과 설치·재실행은 Mac 잠금에 이어 사용자의 PASS 인증 진행으로 대기 중이다. 실행 중인 설치본과 외부 인증 창은 유지한다.
