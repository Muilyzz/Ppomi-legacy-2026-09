# 개인 기록 규격 v1

금융·몸의 측정·식사·운동·컨디션은 같은 대상 ID, 발생 시각, 수집 시각, 출처, 확인 상태를 사용한다. 식비 결제는 식사가 아니며, 음식 사진의 영양 추정은 체성분 기기의 실측값이 아니다. 기록 종류와 측정 항목의 조합을 검증한다.

실제 자료는 `~/Library/Application Support/Ppomi/Private/records.sqlite`에 저장한다. 증빙은 같은 디렉터리의 `record-evidence/`에 복사한다. 공개 저장소에는 예시와 코드만 둔다. JSON·JSON-LD 내보내기는 로컬 파일 생성이며 업로드하지 않는다.

## 가져오기

- [JSON Schema](schemas/life-records.schema.json), [가상 예시 JSON](schemas/life-records.example.json).
- 시각은 `2026-09-06T08:00:00+09:00` 또는 `2026-09-05T23:00:00Z`처럼 시간대가 필수다. 내보낼 때 UTC로 정규화하며 같은 순간을 보존한다.
- 모르는 수치는 해당 metric을 생략한다. 빈 항목을 0으로 바꾸지 않는다. BMI 저장 단위는 `kg/m2`, 표시 단위는 `kg/m²`를 사용할 수 있다. 세포외수분비는 `ratio`다.
- `sourceName`과 `sourceRecordID`가 같고 사실도 같으면 중복으로 처리한다. 내용이 다르면 전체 가져오기를 취소하고 충돌을 알린다. 출처 ID가 없는 수동 기록은 동일 값·시각이어도 자동 합치지 않는다.
- 가져오기는 전부 성공하거나 전부 취소된다. 대상 ID와 증빙 ID를 검증한다. JSON Schema 외에 대상 참조·중복·시각의 달력 유효성·수정 이력을 코드가 검사한다.
- 다른 기기로 옮긴 JSON의 증빙은 메타데이터만 남는다. 원본 파일을 별도로 첨부하기 전까지 로컬 증빙 경로는 없다. JSON 안의 파일 경로를 열거나 복사하지 않는다.

## 대상, 근거, 수정

`person`, `organization`, `account`, `property`, `device`는 표시 이름과 별도로 ID를 갖는다. 두 계좌의 표시 이름이 같아도 같은 계좌라고 추정하지 않는다. 개인과 법인의 자료를 합치지 않는다. 기존 장부에 부여하는 ID는 기존 행의 식별자이며 계좌 소유권의 증거가 아니다.

`method`는 수집 경로: `api`, `ocr`, `manual`, `legacyImport`, `aiEstimate`다. `review`는 `unreviewed` 또는 `userConfirmed`다. 사용자가 확인해도 AI 추정이 실측으로 바뀌지 않는다. **`userConfirmed`는 기록을 검토했다는 뜻이며 결제·실행 승인이 아니다.** 실행 승인 채널과 1회 승인당 1회 탭 규칙은 별도로 유지한다.

수정은 이전 기록 전체·수정 시각·이유를 보관한다. 최초 수집 시각과 출처 ID는 수정하지 않는다. 증빙에는 원본 이름·SHA256·첨부 시각을 보관한다. 실제 파일 경로는 개인 저장소에만 남고 내보내지 않는다.

## Schema.org 연결

[Observation](https://schema.org/Observation)은 수치마다 하나씩 만들고, 대상·발생 시각·측정 항목·값·단위를 연결한다. 사람과 법인은 `Person`, `Organization`, 실제 식사·운동 기록은 [EatAction](https://schema.org/EatAction), [ExerciseAction](https://schema.org/ExerciseAction)에 대응한다. 거래를 임의로 `PayAction`으로 변환하지 않는다.

출처·수집 방법·확인 상태·증빙·수정 이력은 `ppomi:` 확장 어휘를 사용한다. `ppomi:`의 IRI는 `https://ppomi.muilyzz.com/vocab/`이며 식별 용도다. 현재 이 경로가 웹에 배포되어 있다는 뜻은 아니다. `api`와 `ocr`는 수집 방법이므로 신체 측정 기술을 뜻하는 Schema.org `measurementMethod`에 넣지 않는다.

Schema.org 내보내기는 호환성을 위한 표현이다. 모든 소비자가 확장 어휘를 이해하는 것은 아니며, 내부 규칙의 검증은 Ppomi 저장소가 맡는다. 완전한 백업과 다시 가져오기는 원래 JSON 형식을 사용한다.

## 기존 금융 장부 반영

앱의 반영 버튼은 기존 SQLite 장부를 읽기 전용으로 열고 `snapshots`, `transactions`를 공통 기록으로 복사한다. 기존 장부나 기존 금융 화면의 계산은 변경하지 않는다. `holdings`는 이 버전의 반영 범위에 포함하지 않는다.

출처 파일 경로는 비공개 registry에서 UUID에 대응시키고, 내보낸 ID에는 경로를 넣지 않는다. 원본 행 ID·앱·계좌 표시 이름·거래 종류·금액 부호·확인 상태를 보존한다. 시간대 없는 기존 시각은 Asia/Seoul로 명시해 해석한다. 미확인 시각·누락 수치를 0이나 현재 시각으로 대체하지 않는다.

잔액은 앱·원본 계좌 표시를 기준으로 임시 계좌 대상을 만든다. 거래는 해당 앱의 ‘계좌 미지정 거래’ 대상으로 둔다. 표시 이름이 같다는 이유로 잔액 계좌와 연결하거나 개인·법인의 소유를 추정하지 않는다. 기존 `confirmed` 상태도 새 기록에서는 `unreviewed`로 시작한다. 동일 행의 금액이나 원본 정보가 달라지면 충돌을 알리고 기존 공통 기록을 덮어쓰지 않는다.

증빙은 장부 바로 옆 `shots/` 디렉터리의 파일명만 허용한다. 실제 일반 이미지·PDF 파일만 복사하며 절대 경로, 상위 경로 이동, 심볼릭 링크를 사용하지 않는다. 가져온 JSON에는 원본 증빙 파일의 위치가 노출되지 않는다.

## 습관 확인 기록

`kind: "habit"`는 `activityID`, `activityStatus`, `activityDay`, `activityTimeZone`이 필수다. `activityID`는 `^[a-z][a-z0-9._-]{0,99}$` 형식의 안정적인 ID이며 현재 선크림 기능은 `sunscreen`을 사용한다. `activityDay`는 실제 행동 날짜 `YYYY-MM-DD`, `activityTimeZone`은 그 날짜의 시간대 식별자(예: `Asia/Seoul`)다. 다른 기록 종류에는 이 필드를 넣지 않는다. 기존 비습관 JSON에 이 선택 필드가 없어도 그대로 읽는다.

상태는 `completed`(사용자가 했다고 확인) 또는 `retracted`(그 완료 표시를 취소)다. 상태 취소는 기존 기록의 수정 이력으로 남기며 ‘안 했다’는 새 사실을 만들어내지 않는다. 예정·알림 수신·사진·AI 추정으로 완료 처리하지 않는다. 현재 습관 기록은 `method: "manual"`만 허용하고, 건강 효과나 완료율을 metrics에 넣지 않는다.

선크림 카드의 `occurredAt`은 **발랐다고 확인한 보고 시각**이고 `activityDay`는 바른 날짜다. ‘어제 발랐어’를 오늘 보고했다면 실제 행동 날짜는 어제, 보고 시각은 오늘로 분리한다. 실제 도포 시각은 알 수 없으므로 만들지 않는다. `record_health`의 habit는 이 날짜와 시간대를 명시적으로 받아 저장하며 불명확하면 질문한다. 미래 보고 시각, 보고 당시 현지 날짜보다 미래인 행동 날짜, 잘못된 날짜·시간대는 저장하지 않는다. JSON-LD에는 `ppomi:HabitConfirmation`, `ppomi:activityID`, `ppomi:activityStatus`, `ppomi:activityDay`, `ppomi:activityTimeZone`, `ppomi:confirmationTime`으로 표현하고 실제 동작의 `startTime`을 만들지 않는다.

`SunCare`는 기본적으로 Asia/Seoul 달력을 사용한다. 테스트나 다른 지역에서는 명시적 Calendar를 전달할 수 있다. 집계는 보고 시각을 다시 날짜로 바꾸지 않고 저장된 `activityDay`를 사용하므로 늦은 보고나 시간대 변경으로 행동 날짜가 바뀌지 않는다. 같은 사람·같은 행동 날짜에 버튼과 음성 기록이 둘 다 있어도 하루 한 번으로 집계한다. 최근 7일·28일은 기록이 있는 날짜 수이며 빈 날짜는 `unrecorded`다. 빠진 날짜를 실패나 미실행으로 해석하지 않고 노화 방지 효과로 환산하지 않는다. 요약 조회 자체는 기록을 생성하지 않는다. `health_records(activityDay: ...)`로 실제 행동 날짜를 조회할 수 있으며 일반 `since`/`before`는 기록의 보고 시각을 기준으로 한다.

사진 관찰과 습관 확인은 서로 다른 자료다. 선크림 완료 로그는 사진 변화의 원인이나 효과를 증명하지 않는다. 이 버전의 습관 코어는 사진 비교 데이터를 생성하지 않는다.

## 앱에서 사용하기

‘몸과 생활’ 탭에서 인바디 앱의 **더보기 → 인바디결과관리** 목록 또는 측정 상세 화면을 읽는다. 날짜·시각과 항목명이 함께 보이는 값만 가져오며, 화면 밖의 항목은 만들지 않는다. 같은 측정의 상세 화면을 읽으면 기존 기록의 항목을 보완하고 수정 이력을 남긴다. 알려진 측정 기기나 수치가 충돌하면 덮어쓰지 않는다. 화면 시각의 시간대는 Asia/Seoul로 기록한다. 등록 기기는 과거 측정에 사용된 기기를 뜻하지 않는다.

인바디 화면·이미지 가져오기는 현재 연결된 본인 프로필에 한정한다. 가족 JSON을 가져온 경우에는 대상 선택기로 기록과 차트를 분리한다. API 자동 연동과 Apple Health 동기화는 이 버전에 포함하지 않는다.

식사·운동·컨디션은 ‘기록 추가’에서 시각, 메모, 아는 수치와 선택한 사진을 저장한다. 직접 입력과 AI 추정을 구분하고, AI 추정 기록은 7일 요약의 실제 기록 건수·합계에서 제외한다. 차트는 측정된 시점의 점만 표시하고 기기·수집 방식을 구분한다. 관계나 인과를 자동 판정하지 않는다.

원본 근거와 이전 수정값은 기록 상세에서 확인한다. 사용자의 ‘원본과 직접 확인했어요’는 해당 기록의 검토 표시다. 실제 수치가 맞는지는 원본과 대조해야 한다.

## 외부 에이전트와 음성

MCP와 음성은 앱과 같은 비공개 저장소를 사용하는 `health_records`, `record_health`, `inbody_capture` 도구를 공유한다. `record_health`에는 시간대를 포함한 `occurredAt`과 재시도에 유지할 `sourceID`, 사용자 보고(`reported`) 또는 AI 추정(`aiEstimate`)을 명시한다. 모르는 수치는 생략하며, 에이전트 인자로 검토 완료나 실행 승인을 지정할 수 없다. 인바디 캡처는 기존 휴대폰 동의·권한 검사를 먼저 통과해야 한다.
