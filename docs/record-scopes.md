# 개인·사업 구분

회계와 공간 자료는 `RecordScope`를 공통으로 사용한다. 사례별 클래스를 만드는 대신 구분·소유자·사업 ID를 데이터로 명시한다. 같은 사람의 개인 기록과 각 사업 기록은 별도 경계이며, 화면의 ‘전체’는 목록을 보여줄 뿐 통합 잔액을 만들지 않는다.

| 필드 | 의미 |
| --- | --- |
| `kind` | `personal` 개인, `business` 사업, `unclassified` 미분류 |
| `ownerID` | 기록 귀속 주체의 안정적인 참조 ID. 개인/사업 구분에는 필수 |
| `businessID` | 개별 사업을 구별하는 앱 내부 ID. 사업 구분에만 사용하며 필수 |

사업 ID는 사업자등록번호가 아니다. 인증용 가족 프로필·Keychain에 저장한 값은 이 모델이 읽거나 복사하지 않는다. 사업 구분을 지정한 것은 원본 자료의 귀속을 기록하는 것이며, 인증 완료나 세무상 처리 결과를 만들어내지 않는다. 같은 자료 저장소 안에서 같은 사업 ID를 서로 다른 주체에게 연결하면 검증을 거절한다. 회계와 공간 자료 사이에서는 실제 지정한 계정 연결의 주체·구분·사업을 대조하며, 서로 연결하지 않은 자료를 사업 ID만으로 자동 통합하지 않는다.

예를 들어 `ownerID: person:one`인 개인 장부와 `ownerID: person:one, businessID: business:studio`인 사업 장부가 함께 있을 수 있다. 다른 사업에는 다른 businessID를 쓴다. 개인과 사업 사이의 자금 이동은 각각의 장부에서 차대가 맞는 분개로 기록하고 같은 활동 ID로 연결할 수 있다. 활동 ID만 보고 거래를 복제하거나 배분하지 않는다.

## 회계

장부의 `scope`가 경계를 결정하고 계정과 분개는 해당 장부에 속한다. 명시한 scope.ownerID와 기존 book.ownerID가 다르면 거절한다. API와 화면의 개인/사업/소유자/사업 필터는 같은 `RecordScopeFilter`를 사용한다. 책 ID와 필터가 충돌하면 API는 빈 성공 응답으로 숨기지 않고 오류를 반환한다. 과거 평가 ID나 같은 활동 ID를 조회할 때도 구분 경계를 유지한다.

기존 JSON에 scope가 없으면 원문을 바꾸지 않고 미분류로 읽는다. 이름이나 기존 수집 원장의 namespace를 보고 개인 소유나 사업 귀속을 추정하지 않는다. API의 `scopeByBookID`는 누락된 scope도 명시적 미분류로 설명한다. 기존 장부를 같은 ID의 다른 scope로 덮어쓰는 것은 계속 금지한다. 실제 기존 자료의 분류·이동 작업은 별도로 요청된 원본과 귀속 근거가 필요하며 이 기능 추가로 수행하지 않는다.

## 부동산

공간 형상 한 개에 별도의 소유 근거(`ownerships`)와 사용 근거(`usages`)를 연결한다. 개인 명의로 기록된 공간의 사업 사용이나 다른 소유자의 공간 사용도 표현할 수 있다. 소유와 사용을 일치시키거나 형상을 사업별로 복사하지 않는다.

소유 지분·사용 배분 비율은 1/10000 단위의 입력값이다. 입력이 없으면 미입력으로 표시하며 0%·100%·세무상 공제 비율을 추정하지 않는다. 사용 범위별 새 계정 연결은 장부 ID와 계정 ID를 함께 지정하고, 계정 존재·자산 계정 여부·해당 장부 소속·명시한 사용 scope와 장부 scope의 일치를 확인한다. 소유자의 scope와 사용 scope가 같아야 한다는 조건은 두지 않는다.

과거의 자유형 `accountIDs`는 이전 미검증 참조로 보존한다. 이를 새 검증된 연결로 취급하거나 소유·사업 사용을 역추정하지 않는다. 사용 근거가 없는 과거 공간 자료는 미분류에서만 찾을 수 있다. 3D는 구분 필터와 상관없이 같은 원본 형상을 렌더링하며 비율로 형상·금액을 자동 생성하지 않는다.

회계와 공간 저장소의 원본 ID 불변성·원자적 가져오기·예시 미삽입 원칙을 유지한다. 새 경계가 실자료를 임의로 재분류하거나 Keychain의 인증 정보를 내보내지 않는다.
